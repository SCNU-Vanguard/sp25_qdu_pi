# 09-21 D1：C板设备与通信协议核准

本阶段只做源码核对和只读设备检查。未确认实际物理链路与协议前，不运行 `standard`、`cboard_test`、`gimbal_response_test`，不打开串口写端，不发送 CAN 帧，也不修改云台或开火配置。

## 1. 为什么不能直接填写 `DevC-USB`

当前资料中同时存在三套不同接口：

| 接口 | 当前在哪里 | 传输形式 | 当前主程序是否使用 |
| --- | --- | --- | --- |
| `io::CBoard` | `io/cboard.*`、`io/socketcan.hpp` | Linux SocketCAN，固定8字节CAN帧 | `src/standard.cpp`正在使用 |
| `io::Gimbal` | `io/gimbal/gimbal.*` | 串口字节流，`SP`帧头＋packed struct＋CRC16 | `standard`没有使用 |
| 青大 `SharedTopic` | Pi原青大工程及`User/xrobot.yaml` | 逻辑UART `DevC-USB`上的topic协议 | SP25尚未接入 |

`DevC-USB`是青大框架中的逻辑设备名，不能据此断定Linux节点叫`/dev/DevC-USB`，也不能证明其字节协议与SP25 `Gimbal`相同。必须先确认Pi实际枚举出的串口/CAN设备，再查青大设备映射和SharedTopic实现。

## 2. SP25 `CBoard`源码已经能确认的合同

### 2.1 物理接口

- 从YAML读取`can_interface`，现有配置均写`can0`；
- 使用Linux `PF_CAN/SOCK_RAW/CAN_RAW`；
- `SocketCAN`接收所有CAN帧，再由`CBoard`按CAN ID判断；
- `standard3.yaml`只是旧车配置：四元数ID `0x100`、状态ID `0x101`、发送ID `0xff`，不能用于当前C板。

### 2.2 四元数接收帧

配置ID命中`quaternion_canid`时，8字节解释为：

| 字节 | 字段 | 编码 |
| --- | --- | --- |
| 0–1 | x | 有符号int16，大端，除以10000 |
| 2–3 | y | 有符号int16，大端，除以10000 |
| 4–5 | z | 有符号int16，大端，除以10000 |
| 6–7 | w | 有符号int16，大端，除以10000 |

代码随后按Eigen构造顺序`(w,x,y,z)`保存，并检查四元数模长与1的差不超过0.01。时间戳是Pi收到CAN帧时的`steady_clock::now()`，不是C板提供的采样时间。

### 2.3 弹速与模式接收帧

配置ID命中`bullet_speed_canid`时：

| 字节 | 字段 | 编码 |
| --- | --- | --- |
| 0–1 | bullet_speed | 有符号int16，大端，除以100，代码按m/s使用 |
| 2 | mode | 0 idle、1 auto_aim、2 small_buff、3 big_buff、4 outpost |
| 3 | shoot_mode | 0 left、1 right、2 both |
| 4–5 | ft_angle | 有符号int16，大端，除以10000，日志按rad |
| 6–7 | 未使用 | 当前源码忽略 |

当前实现没有检查mode/shoot_mode是否越界，也没有最后收包时间；断流后旧弹速和旧模式会继续保留。

### 2.4 SP25发送帧

发送CAN ID由`send_canid`配置，DLC固定8：

| 字节 | 字段 | 编码 |
| --- | --- | --- |
| 0 | control | 0/1 |
| 1 | shoot | 0/1 |
| 2–3 | yaw | 有符号int16，大端，弧度×10000 |
| 4–5 | pitch | 有符号int16，大端，弧度×10000 |
| 6–7 | horizon_distance | 有符号int16，大端，数值×10000 |

这只是旧SP25源码的协议，尚无证据表明当前青大C板接收相同ID和字段。D1阶段禁止发送该帧。

### 2.5 已确认的安全与稳定性缺口

- `CBoard`构造时同步等待两帧四元数，没有超时；
- `imu_at()`继续等待目标时刻后的姿态，也没有有界失败；
- 弹速、模式和姿态没有online/stale状态；
- `SocketCAN::write()`没有离线门控；
- SocketCAN的文件描述符、`ok_`和退出标志在线程间缺少完整同步；
- 重开后没有连接代次，也没有使CBoard旧状态失效；
- `standard`创建CBoard后会调用`send()`，所以本阶段不能通过运行`standard`来“看看能否通信”。

## 3. SP25 `Gimbal`串口源码已经能确认的合同

这一实现以两个ASCII字节`S`、`P`为帧头，尾部是SP25工具中的CRC16。结构体直接packed后写入串口，浮点数和整数使用主机原生字节序；当前目标Pi是小端ARM64。

- C板到视觉：mode、`wxyz`四元数、yaw/yaw_vel、pitch/pitch_vel、bullet_speed、bullet_count、CRC16；packed长度43字节；
- 视觉到C板：mode、yaw/yaw_vel/yaw_acc、pitch/pitch_vel/pitch_acc、CRC16；packed长度29字节；
- 发送mode：0不控制、1控制但不开火、2控制并开火。

这个类只从YAML读取`com_port`，当前源码没有在这里显式读取/设置波特率。它虽然有`reconnect()`，接收线程却没有调用；首次打开失败会`exit(1)`，构造时等待第一帧四元数也没有超时。它不能直接作为已完成的热插拔方案。

更重要的是：目前没有证据证明青大SharedTopic使用`SP`帧头、上述43/29字节结构或同一CRC。因此不能因为它也是串口就直接复用。

## 4. 青大配置目前只能确认什么

已回收的`User/xrobot.yaml`说明：

- `SharedTopic`和`SharedTopicClient`使用逻辑UART名`DevC-USB`；
- 接收topic包括`gimbal_gyro`、`gimbal_accl`、`gimbal_quat`、`camera_sync_result`、`robot_game_ref`；
- 发送侧已明确列出的topic是`camera_sync_command`；
- 相机使用外触发时，CameraFrameSync还依赖同步命令和同步结果。

这份配置没有给出Linux设备路径、波特率、SharedTopic帧头/CRC/topic ID，也没有证明云台瞄准命令使用哪个topic。需要继续读取Pi原青大工程源码。

## 5. Pi只读核准顺序

1. 列出`/dev/serial/by-id`、`by-path`、`ttyACM*`、`ttyUSB*`和可能的`/dev/DevC-USB`；
2. 单独列出CAN网络接口及其UP/DOWN状态；
3. 用`lsusb`和`udevadm`确认串口设备的VID/PID、序列号和驱动；
4. 在青大源码中找到`DevC-USB`到Linux设备的映射；
5. 找到SharedTopic的串口参数、帧解析、校验和topic ID定义；
6. 找到云台控制输出对应topic和数据结构；
7. 整理为最终协议表后，才决定SP25应适配SharedTopic、串口Gimbal还是SocketCAN。

所有这些检查都不读取串口数据、不占用设备、不发送任何内容。

## 6. 第一个Pi命令

在树莓派Bash执行下面一整行：

```bash
ls -l /dev/DevC-USB /dev/serial/by-id /dev/serial/by-path /dev/ttyACM* /dev/ttyUSB* 2>&1
```

这条命令只列出可能的串口设备及符号链接：

- `ls -l`显示文件和符号链接目标；
- `/dev/serial/by-id`通常按USB设备身份稳定命名；
- `/dev/serial/by-path`按物理USB端口命名；
- `ttyACM*`、`ttyUSB*`是常见临时设备节点；
- `2>&1`让“不存在”的提示也一起出现在复制结果中。

它不会打开串口，不会读取C板数据，也不会发送控制。输出必须原样回收；不能仅凭出现`ttyACM0`就认定它一定是C板，因为相机、调试器或其他USB设备也可能创建节点。

### 6.1 2026-09-21现场结果

Pi实际输出确认：

```text
/dev/DevC-USB                         不存在
/dev/ttyUSB*                          不存在
/dev/ttyACM0                          存在，root:dialout，字符设备166:0
/dev/serial/by-id/usb-QDU-Future_MainCtrl_QDU-Future-MainCtrl-89ABCDEF0123456701234567470054000E50485939373620-if00
  -> ../../ttyACM0
```

因此当前插入的青大主控板以USB CDC ACM串口出现，设备身份字符串明确包含`QDU-Future_MainCtrl`。`DevC-USB`不是现成的Linux设备节点，应是青大框架中的逻辑UART名称或映射键。

后续生产配置不能写死`/dev/ttyACM0`：这个编号可能在重新插拔或增加其他ACM设备后变化。优先使用上述`/dev/serial/by-id/...`稳定链接，或者核对青大框架怎样把该by-id设备映射为`DevC-USB`。

这项结果强烈支持SharedTopic走USB串口，但还不能排除Pi同时存在独立CAN接口。下一项只读列出CAN网络设备，判断SP25现有`can0`是否有实际硬件基础。

### 6.2 接线照片与最终物理链路判断

用户提供的`pics/7.jpg`显示：树莓派侧USB转串口设备通过四线连接到RoboMaster C板的`UART1`，照片中C板`CAN1/CAN2`接口没有接线。结合Linux枚举出的`QDU-Future_MainCtrl -> ttyACM0`，当前实际业务链路已经可以确定为：

```text
Raspberry Pi USB
  → QDU-Future USB CDC ACM设备
  → /dev/ttyACM0（稳定入口使用/dev/serial/by-id/...）
  → TTL UART连线
  → C板UART1
```

因此不再把“是否存在can0”作为决定当前C板后端的前置条件：即使Pi另有CAN控制器，照片中的实际C板通信也没有走CAN线。SP25现有`io::CBoard + SocketCAN`不能原样用于这套接线。

工程内旧`io::Gimbal`同样不能直接认定兼容。它使用固定`SP`帧头和packed结构体；青大配置明确使用SharedTopic，尚无证据证明两者帧格式、CRC和字段相同。

### 6.3 已确定的适配方向

保持SP25的Camera、YOLO、Tracker、Solver、Target和Aimer不变，通信层采用青大SharedTopic串口协议，并向上提供SP25需要的统一状态与命令接口。预计修改边界为：

1. 新增或整理一个SharedTopic C板后端，串口使用稳定`/dev/serial/by-id/...`路径；
2. 接收`gimbal_quat`及后续确认的弹速、模式、裁判信息，并提供有时间戳和新鲜度检查的状态；
3. 将SP25 `io::Command`转换为青大实际控制topic；在控制topic未找到前不实现发送猜测；
4. `standard`只依赖统一C板接口，不保留运行时同时打开SocketCAN和SharedTopic；
5. 增加断连、重连、热插拔、半包、坏CRC和数据过期测试；
6. 新建Pi整车YAML，固化by-id路径且`auto_fire: false`，不复用`standard3.yaml`旧CAN ID。

开始编码前还必须从青大源码确认：串口波特率、SharedTopic外层帧格式、校验、topic名称到ID映射、每个payload的结构/单位/字节序，以及云台控制输出topic。物理串口已经确定，但这些字节协议不能凭照片推断。
