# 09-21：SP25 完整入口、海康运行库与 QDU C 板通信阶段总结

本文记录 2026-09-21 这一阶段从“检查 SP25 通信是否已经适配”到“完整 `standard` 能启动相机，
但真实 C 板上行零字节”的全部修改、排查证据和当前边界。本文是下一次继续工作的首要入口；
协议实现细节另见 [QDU SharedTopic 通信实现与只读验收](9.21-qdu-shared-topic-implementation.md)。

## 1. 当前最准确的结论

本阶段已经完成并真机确认：

1. SP25 普通 `standard` 入口已接入 QDU USB CDC / SharedTopic 通信后端；
2. Linux 使用稳定的 `/dev/serial/by-id/...` 设备路径，而不是可能随插拔变化的 `/dev/ttyACM0`；
3. 主机侧协议编解码、姿态过期门控、断连重连、热插拔状态清理和正常命令发送已实现；
4. 自动测试覆盖协议、模拟热插拔以及同时 100 Hz 收姿态和发送非零目标；
5. 生产 IO 已收敛为当前实车使用的 HikRobot 相机，不再把 MindVision、普通 USB Camera 和
   `libMVSDK.so` 链入 `standard`；
6. 完整工程海康运行库不匹配的问题已经定位并永久修复；
7. 不使用 `LD_PRELOAD` 的根工程 `camera_test` 已真机取得 720×540 BGR 图像并稳定约 100 FPS；
8. 完整 `standard` 已成功完成 Hailo 模型加载、海康相机启动和 QDU 串口打开。

当前仍未通过：

1. 真实 C 板虽然能被 Linux 识别并成功打开串口，但 15 秒只读监视中收到 **0 个原始字节**；
2. 因为没有四元数，`standard` 的安全门控在检测之前提前跳过，Tracker、Solver、Aimer 和正常
   非零控制命令尚未在这次完整入口中实际运行；
3. 真实 C 板 RX、同时收发、拔插恢复和长期稳定性仍未验收；
4. 当前镜头标定、手眼外参、云台方向和执行机构仍未接入实车验证；
5. 原第 11 部分完整性能统计继续暂缓。

因此不能把本阶段写成“整套自瞄已经完成”。准确表述是：

> 完整软件入口已经能启动 Hailo、相机和 QDU 串口；相机永久修复并通过短时真机取图。真实
> C 板到 Pi 的应用数据流当前完全静默，整链停在姿态输入门控处。

## 2. 当前硬件和连接

现场当前只有：

```text
Raspberry Pi 5 + HAILO8L
    ├── USB → HikRobot MV-CS016-10UC，相机序列号 DA6589759
    └── USB → QDU-Future_MainCtrl USB CDC → C 板 UART1
```

目前没有接入云台、发射机构等执行器。Linux 枚举结果为：

```text
/dev/serial/by-id/
  usb-QDU-Future_MainCtrl_QDU-Future-MainCtrl-89ABCDEF0123456701234567470054000E50485939373620-if00
  -> ../../ttyACM0
```

`/dev/ttyACM0` 是本次临时编号，正式配置使用上面的 by-id 路径。C 板亮灯只证明供电；出现
`ttyACM0`只证明 USB CDC 枚举；`serial_open=1`才证明 Linux 进程成功打开设备；`bytes>0`才
证明 C 板确实向 Pi 发送了数据。这四层不能混为一谈。

## 3. 通信适配做了什么

### 3.1 先审计并淘汰不适用的旧路径

原 SP25 同时存在：

- `io::CBoard + SocketCAN`：普通 `standard/uav/sentry` 使用；
- `io::Gimbal + SP packed 串口帧`：MPC 和部分调试入口使用。

现场接线没有走 CAN，青大配置明确使用 `DevC-USB` / SharedTopic，因此旧 CAN ID、`can0`、
`/dev/gimbal`、`SP`帧头和旧 packed 结构都不能直接使用。代码审计记录见
[当前代码包通信适配审计](9.21-communication-code-audit.md)。

### 3.2 新增 SharedTopic 字节协议

新增：

- `io/qdu_shared_topic_protocol.hpp`
- `io/qdu_shared_topic_protocol.cpp`

实现内容包括：

- `0x5A`前缀、版本、24 位 payload 长度、topic CRC32、48 位微秒时间戳和两级 CRC8；
- 小端多字节字段；
- 任意拆包、粘包、帧前噪声和坏包后的重新同步；
- payload 长度上限，避免坏长度造成无界等待或分配；
- topic 名称 CRC32；
- `ahrs_quaternion` / `gimbal_quat` 四元数接收；
- `target_euler` 和 `fire_notify` 命令编码。

### 3.3 新增真实串口、状态和重连后端

新增：

- `io/qdu_shared_topic.hpp`
- `io/qdu_shared_topic.cpp`

它负责：

- 以 115200、8N1、无流控打开稳定 by-id 设备；
- 初次设备不存在时持续重试，而不是退出；
- 断开后关闭旧对象、清空解析半包、姿态缓存和旧控制意图，再重新打开；
- 统计打开、断开、字节、包、四元数、未知 topic、坏 CRC、TX 和被门控命令；
- 将收到姿态的主机 `steady_clock` 时刻用于有界插值；
- 超过 250 ms 未收到姿态时将 IMU 判为 stale；
- stale、断线、无目标、非有限数、重连和正常退出时清除目标并保持 `fire=false`；
- 重连后的第一组输出固定为零目标和禁火，避免重放断线前命令。

### 3.4 保留 SP25 上层框架

修改 `io/cboard.*` 和 `io/gimbal/gimbal.*`，保留 SP25 上层调用接口，内部统一改走 QDU 后端。
因此 Camera、YOLO、Tracker、Solver、Target、Aimer 的主体没有被另一套青大自瞄程序替换。

`src/standard.cpp`增加：

- `--seconds=N` 有界运行；
- 姿态不新鲜时不把旧姿态交给 Solver/Tracker；
- 每秒报告帧号、检测数、目标数、控制状态、yaw/pitch、RX/TX 和抑制数；
- 正常退出时经析构发送禁火和清除目标；
- 分阶段启动：先加载 Hailo/SP25 算法对象，再启动相机并等待第一帧，最后打开 QDU。

新增 `configs/pi_standard3_qdu.yaml`作为当前 Pi 完整入口。它保持：

- `auto_fire: false`；
- 当前 DA6589759 相机、720×540、100 FPS、软件旋转 180 度；
- Hailo `szu-int16-head-l` 和现有灯条修正；
- QDU by-id、115200 8N1、250 ms 姿态失效门限；
- `tx_enabled: true`，但没有新鲜姿态时生产代码不会发送正常控制命令。

其他兵种配置统一加入 `qdu_communication`，默认 `tx_enabled: false`，先用于只读验收。

## 4. 自动测试和编译整理

`tests/communication`提供：

2. `qdu_hotplug_sim_test`：PTY 模拟 100 Hz 姿态、断开、重建设备和恢复接收；
3. `qdu_normal_tx_sim_test`：同一伪串口一边 100 Hz 发姿态，一边验证生产 `CBoard::send()`

这些测试证明主机代码对模拟的合法字节流工作正确，不代替真实 C 板验收。

- 根 `CMakeLists.txt`不再构建无关普通 USB Camera 测试；
- 最终 `standard`只加载海康 `libMvCameraControl.so`，不再加载 MindVision `libMVSDK.so`。

同时清理两项 GCC 14 提示：

## 5. 完整工程相机故障如何定位和修复

### 5.1 最初现象

独立 `build/pi-camera/hik_camera_test`可以稳定 100 FPS，但根工程 `standard`在海康枚举阶段持续：

```text
EnumDevices(USB) failed: 0x80000006
```

`0x80000006`在随库头文件中是 `MV_E_RESOURCE`，即资源申请失败。

### 5.2 被证据排除的假设

先后做了两项必要修改，但它们不是最终根因：

1. 移除 MindVision/MVSDK，避免两套相机 SDK 同进程；
2. 改成 Hailo 先加载、相机后启动、相机首帧后再打开 QDU。

两项修改保留，因为它们符合当前单海康硬件和确定性启动要求；但修改后 `standard`仍失败，说明
不能把错误继续归因于异厂 SDK 或并发初始化。

### 5.3 最小对照锁定运行库

使用根工程的 `build/pi-standard/camera_test`，不加载 Hailo、Tracker、Aimer 或 C 板，仍然返回
`0x80000006`。这把范围缩到根工程相机封装/运行库。

进一步对照 `ldd`发现：

- 成功的独立相机测试使用青大参考工程随附的海康 ARM64 运行库；
- 失败的根工程使用 SP25 仓库原来的另一份同名 `libMvCameraControl.so`。

用 `LD_PRELOAD`只替换运行库后，同一个根工程 `camera_test`立即成功取图并稳定约 100 FPS。
因此最终根因是仓库内原 ARM64 海康运行库不适配，不是相机代码、相机参数、Hailo 或 QDU。

### 5.4 从临时验证变为永久修复

只替换主库后的第一次永久测试返回：

```text
EnumDevices(USB) failed: 0x8000000c
```

随库头文件将其定义为 `MV_E_LOAD_LIBRARY`。检查运行库字符串和完整 SDK 目录后确认，主库会在
运行时动态加载 USB 传输和图像处理组件。因此工程补齐下列 7 个文件：

| 文件 | 大小（字节） | SHA-256 |
| --- | ---: | --- |
| `CommonParameters.ini` | 3,582 | `3FD5DCCFDEAC74B05C84AEEEECFEC9E17FE293DA4109E821BAC0E878434DD518` |
| `libFormatConversion.so` | 5,149,644 | `7D9CE8AFD1329314F1DA7ACE7D8C367373F28C33EA7F235711DB74E9D776F027` |
| `libMediaProcess.so` | 2,179,080 | `810149115C45E3887E289C7880B60AE33A4F451868DF2E57A103C06C08E9FAE7` |
| `libMvCameraControl.so` | 7,569,576 | `C2EEC98418DB2675B21641BB8FD78D3484B0E64C803784CC2E3C3631C9BAEC58` |
| `libMVRender.so` | 715,000 | `17F26F65FC5B64EE0E4D99F4DCC15B54995B9F6F43887D308F8CF3C2A985BF43` |

GigE 相机后端。

`io/CMakeLists.txt`标注 `[9.21-PI-HIK-SDK]`：

- 按绝对路径链接仓库内唯一主库，不让链接器静默选择系统中另一版本；
- ARM64 配置阶段检查全部 7 个组件，缺件立即列出路径；
- 正式程序不依赖 `LD_PRELOAD`，也不依赖外部参考工程目录。

### 5.5 永久修复真机证据

不设置 `LD_PRELOAD`运行根工程 `camera_test`：

```text
output=720x540, BGR8
grabbing serial=DA6589759
capture=100.0 FPS, deliver=100.0 FPS
received 303 images
camera_exit_code=0
```

用户约 3 秒后人工 Ctrl+C；启动后的稳定窗口为 100 FPS，`capture_timeouts=0`、
`pool_dropped=0`、`consumer_skipped=0`、`reconnects=0`。这是短时永久修复验收，不是长稳测试。

`XOpenDisplay Fail`来自海康运行组件在无图形 SSH 环境尝试连接显示器；本次取图、BGR转换和
帧率正常，不是相机失败。

## 6. 完整 `standard` 真机运行结果

运行：

```bash
./build/pi-standard/standard configs/pi_standard3_qdu.yaml --seconds=30
```

用户回收的启动和前约 10 秒日志证明：

1. Hailo 和 SP25 算法对象完成构造；
2. HikRobot 输出 720×540 BGR、100 FPS 配置，序列号 DA6589759；
3. `standard`收到相机 sequence=1 后才启动 QDU；
4. QDU 使用正确 by-id、115200 8N1、TX enabled、250 ms stale 门限；
5. 相机帧号约每秒增加 100，说明完整进程内相机继续稳定取图；
6. QDU 约 5 秒后成功打开串口；
7. `rx_q=0`，所有正常控制意图均被抑制，`tx=0`。

这里不能写成“完整自瞄主循环已跑通”。当前 `src/standard.cpp`在 `imu_fresh()==false`时于
Detector 之前 `continue`，所以此次仅证明 Hailo模型加载、相机取图、QDU启动和安全门控；没有
实际执行本轮 YOLO、Tracker、Solver、Aimer。用户没有提供 30 秒结束汇总和退出码，不补写。

## 7. 真实 C 板只读结果及其含义

第一次监视时同时残留两个会打开串口的程序，`serial_open=0`。用户结束这两个进程后，独占运行：

```bash
./build/pi-communication/qdu_link_monitor configs/standard3.yaml --seconds 15
```

最终结果：

```text
serial_open=1
opens=1
disconnects=0
bytes=0
packets=0
quaternions=0
ahrs_q=0
gimbal_q=0
invalid_q=0
unknown_topics=0
crc_header=0
crc_payload=0
tx_commands=0
```

这能确定：

- USB CDC 枚举正确；
- by-id路径正确；
- `xiao`用户有权限；
- 监视器成功打开串口；
- 15秒内 C 板到 Pi 没有任何应用字节。

因此现在不能去调CRC、topic名称、payload顺序或四元数范围，因为解析器没有输入。也不能把
`bytes=0`解释成解析失败；解析失败至少会有 `bytes>0`。

对照 xrobot-org 官方
[SharedTopic](https://github.com/xrobot-org/SharedTopic/blob/489d05938f4b8b24ab950789decb4b43393e8d46/README.md)
和
[SharedTopicClient](https://github.com/xrobot-org/SharedTopicClient/blob/43365ed2718573f35fe3fdbaadfe4a7565453233/README.md)：

- 接收端直接阻塞等待UART数据，然后调用 `Topic::Server::ParseData()`；
- 发送端订阅板端本地Topic，每次本地Topic发布时直接打包写UART；
- 没有“Pi先发订阅请求，C板才开始上报”的握手。

所以当前更可能是：

1. C板固件没有实例化发往 DevC-USB 的 `SharedTopicClient`；
2. 固件没有把 `ahrs_quaternion`或`gimbal_quat`列入转发配置；
3. 当前没有接云台/IMU，板端没有产生对应本地Topic，因此没有触发发送；
4. C板烧录的固件不是与该Linux自瞄配置配套的版本。

Pi 在 `standard`启动时已经发送过安全的零目标和 `fire=false`；协议没有ACK，这不能证明C板
应用层已经解析。真实非零TX没有发生，因为姿态门控未通过。

## 9. 下一次从哪里继续

下一步不是继续改 Pi 解析器，而是取得当前 C 板电控工程或明确其固件配置，检查：

```text
SharedTopicClient
DevC-USB
ahrs_quaternion
gimbal_quat
对应 IMU/云台 Topic 发布者
```

建议顺序：

1. 确认 C 板当前烧录的工程、分支和运行配置；
2. 核对板端是否实例化 `SharedTopicClient`并绑定 DevC-USB；
3. 核对无云台接线时是否仍有板载 IMU 四元数发布；
4. 先让 `qdu_link_monitor`出现 `bytes>0`；
5. 再按 `packets/unknown_topics/invalid_q/quaternions`逐层核对真实协议；
6. 四元数持续更新后，做真实断连、重连和USB热插拔；
7. 再运行 `standard`，确认检测、Tracker、Solver、Aimer和正常禁火TX真正进入；
8. 最后进行当前镜头标定、手眼标定、方向、延迟和执行机构验收。

在取得板端工程前，不应：

- 凭空增加订阅握手；
- 反复修改波特率、CRC或topic名；
- 用持续发送零值掩盖RX为零；
- 宣称真实收发或整套自瞄已经通过；
- 接入云台/发射机构或开启自动开火。
