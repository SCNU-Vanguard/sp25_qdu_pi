## 已核实的差别

1. 原包 `tasks/auto_aim/yolo.cpp` 根据 `yolo_name` 选择YOLOv5/v8/11，并非只有一种检测流程。
2. 原包 `configs/demo.yaml` 为 `yolo_name: yolov5`、`use_traditional: true`、模型路径 `assets/yolov5.xml`。不能据演示配置断言用户以往所有运行都开启此功能。
3. 原包 `tasks/auto_aim/yolos/yolov5.cpp` 完成NMS、名称/大小板检查后明确调用：

   ```cpp
   // 使用传统方法二次矫正角点
   if (use_traditional_) detector_.detect(*it, bgr_img);
   ```

4. 原包 `tasks/auto_aim/detector.cpp` 的上述重载在候选附近找亮灯条，检查几何形状，把网络角点与灯条端点比较；满足条件才替换四角点。这是OpenCV图像处理，不需要为此恢复OpenVINO神经网络推理。
5. 原修正逻辑有严格限制：要求ROI完整在图内、找到至少两根灯条、四端点距离总和<15像素。它不是对任意歪框的万能修正，直接照搬不保证能修好image_2中的大偏差。旧实现只改 `armor.points`，移植时须按当前Armor约定一致更新中心、包围盒、尺寸判断等几何信息，不能留下互相矛盾的字段。
6. 当前 `tasks/auto_aim/yolo.cpp` 为图像resize到640×512、BGR→RGB、Hailo推理、模型解码，直接返回Armor；没有上述灯条二次修正。原YOLOv5为640×640的OpenVINO路径，现在加载青大HEF，不能把当前识别质量当作原模型质量的自动继承；没有证据证明两者权重/输出行为相同。
7. 当前 `tests/camera_detect_test.cpp` 仅相机→YOLO→画出本帧所有Armor；没有创建Solver/Tracker/Aimer。`src/standard.cpp` 和 `tests/auto_aim_test.cpp` 才包含检测后调用SP25 Tracker的链路。
8. 当前SP25 Tracker保留目标状态和预测，有lost/detecting/tracking/temp_lost状态；标准入口返回其维护的目标。它跟踪目标车并关联装甲，不等于永远只允许检测出一块装甲；短暂漏检容忍和丢失条件须按实际情况验证。

## 对前一轮修改的准确表述

- 相机180度修正已由新截图看到图像正立，解决方向问题。
- 最新 `--sample-dir` 只增加最多3组同帧原图/结果的证据保存，不修角点或稳定跟踪。
- `pi_hailo_nms035_review.yaml` 是独立去重候选，正式NMS仍0.5；没有取得候选在Pi的结果。
- 所以不能称“检测效果已修复”，也不能用隐藏其他框或最高置信度选择冒充稳定锁定。

## 后续实际修复顺序

1. 以同一原始帧核对Hailo坐标解码；若坐标解码有错应先修复，不能用灯条处理掩盖模型适配错误。接回原SP25基于灯条的角点修正/几何检查这项功能，仅移植所需图像处理部分，适配当前720×540及当前Armor数据约定；实际灯条支持不足时不能编造角点。
2. 对同一块板的候选进行去重：结合修正后的几何，必要时用同一对灯条的对应关系判重；不同真实装甲仍应保留。候选NMS0.35用于对照，不是完整最终方案。
3. 在方向对应的标定、姿态/时间和接口核准后接入已有SP25 Tracker；连续帧保持同一目标，允许有限短时漏检，失去目标后按状态退出。预览明确区分检测结果和选中/跟踪目标。
4. 单板验收要求只输出一个有效检测、四点贴合灯条，移动时保持目标关联；随后检查多板、遮挡及重现，不承诺“任何场景永不丢失”。一张截图无法证明时间上的稳定锁定。

这条路线保留SP25上层及Hailo运行时，不重写另一套自瞄框架。灯条修正、最终去重和实时Tracker接入尚未完成；本轮是查明原流程差别并解释解决方案。此前原图留样功能仍可用于后续同图验证，原视频A2/300秒长稳/原第11部分继续暂缓。
