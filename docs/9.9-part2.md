## 运行时如何工作

构造时一次完成：

1. 检查运行库确为 4.23.0，读取 HEF，确认 HEF 和物理设备架构为 HAILO8L。
2. 检查只有一个网络组、一个网络、一个图像输入和三个原始输出。
3. 创建一块设备的 VDevice，配置 PCIe、batch size 1，使用显式网络激活。
4. 创建输入/输出 vstream，固定主机数据布局为 NHWC，读取真实名称、shape、格式和量化参数。
5. 将输出按 stride 排序，校验 SDK 返回的实际字节数，预分配三个原始缓冲区和融合矩阵，绑定可复用的 MemoryView/map。

每帧调用 `runtime.infer(rgb, fused)`：检查输入 → 同步执行一帧推理 → 检查数据流状态 → 反量化和融合 → 返回共享的输出视图。

资源按依赖关系释放：激活对象、数据流、主机缓冲、网络和设备均由 RAII 管理；中途构造失败也会释放已创建资源。SDK 超时或流中止后，实例进入失败状态，必须由调用方重建，避免不同输出错配到不同帧。失败时抛出明确错误并清空本次输出。

同一实例用于一个处理线程。输入必须为尺寸正确、连续存储的 `CV_8UC3 RGB`；相机的 BGR 图像需要由调用侧转换。输出与运行时共享内存，下次推理会覆盖；跨帧保存由调用方显式 `clone()`。

## 模型结构约定与尚待确认的内容

当前默认预期来自 `9.9.md` 的设计，尚未取得目标 HEF 的实际解析结果：

| 项目 | 当前实现接受的约定 |
| --- | --- |
| 输入 | 默认 640×512，3 通道 UINT8，调用方提供 RGB 原始像素 |
| 输出布局 | 主机侧 NHWC，不允许转置标志 |
| 三个输出网格 | 默认输入下分别为 80×64、40×32、20×16，即 stride 8、16、32 |
| 每个网格的特征数 | 66＝3 个候选×22 个原始值 |
| 融合结果 | 默认为 `20160×22`、`CV_32FC1` |
| 融合顺序 | stride 8/16/32 → y → x → anchor → 每候选的 22 个值 |
| 量化参数 | 整数输出接受每张量 1 组或逐特征通道 66 组，检查零点、正比例因子及有限范围 |

输入预期尺寸可通过 `HailoRuntimeOptions.expected_input_size` 指定，但必须与 HEF 相符且宽高均为 32 的倍数。设备测试程序当前使用默认 640×512 合同。代码没有硬编码输出层名字，按真实名称绑定数据，按网格尺寸确定尺度。

**尺寸/类型符合只证明结构可读取，不证明语义正确。** RGB 顺序、输入归一化是否已经编入 HEF、66 个通道是否按连续的 3×22 排列、角点是否还需 grid/anchor 解码等，仍须核对同一份 HEF 的导出流程及真实结果。若模型输出数、形状或量化结构不同，程序会拒绝它，而不会把另一类模型强行解释为当前格式。

## 量化与性能边界

- 默认使用自动输出类型，读取 SDK 实际返回的 UINT8/UINT16；CPU 按 `(value - zero_point) * scale` 转为 FLOAT32。
- 可请求 FLOAT32 输出，此时由 SDK 转换，本工程直接使用，不重复反量化。
- HailoRT 4.23 的旧 quantized 布尔参数和标志已弃用，是否转换由源/目标类型决定，代码没有依赖旧标志的作用。依据：[4.23.0 格式及量化定义](https://github.com/hailo-ai/hailort/blob/v4.23.0/hailort/libhailort/include/hailo/hailort.h)。
- 三个输出缓冲和融合矩阵由本工程复用；UINT16 三头情况下，原始输出约 0.85 MiB，融合矩阵约 1.69 MiB。这些仅是本模块的输出存储，不含 SDK、输入图像和整个程序的内存。
- 当前采用 SDK 的同步 `InferVStreams`。官方实现内部仍有每次调用的线程与临时容器开销，不能声称整条推理调用“零分配”。它还会跳过部分 `STREAM_ABORT` 状态，因此本工程额外检查流是否中止。依据：[4.23.0 InferVStreams 实现](https://github.com/hailo-ai/hailort/blob/v4.23.0/hailort/libhailort/src/net_flow/pipeline/inference_pipeline.cpp)。

这些措施减少本工程每帧重复初始化和大块缓冲申请，是否满足完整链路 70–80 FPS，仍需结合后续前处理、Decoder、相机和上层算法在 Pi 上测量。若 SDK 调用开销成为实际瓶颈，再按阶段数据决定是否改为持久数据流工作线程。

## 已执行验证

1. 使用官方 `v4.23.0` 公共头文件，对 `hailo_runtime.cpp` 完成 C++17 语法与类型编译检查，启用 `-Wall -Wextra -Wpedantic`，通过。
2. `hailo_runtime_test.cpp` 的独立编译检查通过。
3. WSL Ubuntu 22.04、GCC 11.4.0、OpenCV 4.5.4 下完成输出测试的编译和 CTest，启用 AddressSanitizer 与 UndefinedBehaviorSanitizer，通过（1/1 测试入口）。覆盖：
   - 完整 `20160×22` 结果逐值校验，故意打乱流顺序及名称排序；
   - UINT8、包含大于 32767 数值的 UINT16、FLOAT32；
   - 非整数零点、逐通道量化、FLOAT32 不二次反量化；
   - 100 次融合的原始缓冲和结果地址保持不变，新帧值确实覆盖旧值；
   - 错误输出数量、重复名字/尺度、错误尺寸/通道、缺失或非法量化参数、NaN/Inf 等拒绝路径。
4. 尝试配置独立设备测试，当前 WSL 找不到 HailoRT 4.23.0 开发包，按预期停在 `find_package(HailoRT ...)`；未安装运行库或驱动，没有完成设备测试的实际链接或运行。

## 验证命令

在工程根目录、Linux/WSL 上运行无硬件测试：

```bash
cmake -S tests/hailo -B build/hailo-tests -DCMAKE_BUILD_TYPE=Debug
cmake --build build/hailo-tests -j2
ctest --test-dir build/hailo-tests --output-on-failure
```

在具有 HailoRT 4.23.0 开发包的目标 Pi 上构建设备测试：

```bash
cmake -S tests/hailo -B build/hailo-runtime \
  -DSP_BUILD_HAILO_DEVICE_TEST=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build/hailo-runtime -j2
ctest --test-dir build/hailo-runtime --output-on-failure
```

先用硬件说明中的实际 HEF 路径执行 `hailortcli parse-hef`，核对上述结构。然后替换下面的 HEF 和图片路径进行测试：

```bash
./build/hailo-runtime/hailo_runtime_test /path/model.hef /path/armor.jpg 100 native
# 对比由 SDK 转为 FLOAT32 的输出路径：
./build/hailo-runtime/hailo_runtime_test /path/model.hef /path/armor.jpg 100 float32
```

测试预处理同一张图片一次，预热 10 帧，再统计指定帧数的原始推理＋融合耗时（平均、p95、最大）。`raw_infer_and_fuse_fps` 明确排除了相机、图像预处理、Decoder、Tracker 和 Aimer，不能当成完整自瞄帧率。
