## 2. 起点：为什么先把检测层单独拆出来

开始本轮时，Pi 独立检测已经完成编译、原 5 项合同测试和真实静态检测。已确认当前模型不是原 NX 上 SP25 使用的 `assets/yolov5.xml`，而是青大工程随附的 Hailo 部署文件：

```text
/home/xiao/workspace/current/pi-camera-249fps-20260822-product-arm64/
source-live/Modules/ArmorDetector/model/szu_int16_head_l.hef
```

它面向 HAILO8L，输入为 RGB UINT8 640×512，三个输出头融合为 20160×22。当前前处理是 720×540 或其他原图直接拉伸到 640×512，再做 BGR→RGB；不做 letterbox，也不除以 255。类别映射与青大参考实现一致：0 为哨兵，1–5 为对应编号，6 为前哨，7/8 为基地。

先用独立入口验证的原因是：如果相机、模型、Tracker、解算、通信和控制同时启动，任何失败都会混在一起。先证明每层合同和数据形状正确，后面真机故障才能定位到具体层，而不是靠猜测修改阈值或硬件参数。

## 3. A：连续视频检测

### 3.1 遇到的操作问题

最初出现过两类“文件不存在”：

- 在 `/home/xiao` 运行 `cmake -S tests/hailo ...`，相对路径被解释成 `/home/xiao/tests/hailo`；实际工程在 `/home/xiao/sp_vision_25-main`。
- 构建成功后仍在错误目录执行 `./build/pi-hailo/hailo_detector_video_test`，Bash 自然找不到可执行文件。

这不是源码或 Hailo 故障。解决方式是先进入工程根目录，或始终使用 `/home/xiao/sp_vision_25-main/...` 绝对路径。后续命令也明确区分电脑 PowerShell 和 Pi Bash。

### 3.2 为什么新增视频验收入口

静态测试只是对同一张图片反复推理，不能证明顺序读取变化画面时不会复用旧帧、提前结束或发生偶发长延迟。因此新增 `tests/hailo_detector_video_test.cpp`，复用生产 YOLO，并明确区分：

- 纯检测耗时；
- 读视频、解码和检测的整体吞吐；
- 性能模式与保存抽帧模式。

程序检查正式处理帧数，读帧失败后不再次推理旧图；抽帧模式单独运行，不把 PNG 写盘时间混进速度基准。

### 3.3 实际结果

`assets/demo/demo.avi` 完整处理 687/687 帧，退出码 0：

| 指标 | 结果 |
| --- | --- |
| 完整 YOLO 检测 | 107.646 FPS |
| 检测平均 / p95 上界 / 最大 | 9.290 / 9.400 / 20.753 ms |
| 视频读取＋检测 | 54.935 FPS |
| 读帧＋检测平均 / p95 上界 / 最大 | 18.202 / 18.900 / 29.545 ms |
| 空检测帧 / 多检测帧 / 总结果 | 146 / 200 / 795 |

这证明连续推理和速度通路正常，但空框和多框数量不能直接证明识别正确。末尾出现一次 MJPEG `overread 8`，仍完成全部帧；记录为素材/解码警告，没有误写成 Hailo 错误。

### 3.4 抽帧暴露的问题

抽查 0、100、400、500、600、686 帧后发现：

- 第 400 帧同一左侧装甲有两个候选；当前 NMS IoU 0.5 下两框 IoU 约 0.413，中心距离也没有达到现有重复阈值，所以两个都被保留。
- 临时把 NMS 调到 0.4 能从 3 框降到 2 框，但不能证明其他场景不会误删真实目标，因此没有直接修改正式配置。
- 第 500、600 帧把置信度从 0.8 临时降到 0.5 后各出现一个候选，说明原空结果至少部分来自门限，但降低门限也可能引入误检，因此正式置信度仍保持 0.8。

这一步形成的原则是：参数对照用于判断原因，不把“框少了”当成修复，也不同时改置信度、NMS、曝光和模型。

## 4. B：真实海康相机

### 4.1 `TriggerSelector=FrameStart` 错误

首次取图反复出现：

```text
TriggerSelector=FrameStart failed: 0x80000004
received 0 images
```

当前相机运行的是自由运行模式 `external_trigger=false`。`TriggerSelector=FrameStart` 只在外部触发模式下是必要配置；旧驱动却在自由运行时也写这个节点，使相机在开始采集前退出。

修复位于 `io/hikrobot/hikrobot.cpp`：

- 自由运行严格设置 `TriggerMode=Off`，不再写 `TriggerSelector`；
- 外触发仍必须选择 `FrameStart`，不能为了绕过错误而吞掉所有节点设置失败；
- `tests/hikrobot_driver_test.cpp` 增加自由运行和外触发故障回归。

这样解决的是错误的条件分支，没有改变曝光、帧率、抽取、Hailo 或 SP25 上层。

### 4.2 `DecimationHorizontal=0x80000109` 错误

通过触发设置后，程序继续在抽取节点失败。Pi 随青大工程的 SDK 头文件确认：

```text
0x80000109 = MV_E_GC_NODE_NOT_FOUND
```

关键证据不是“相机一定不支持抽取”，而是青大原驱动通过数值枚举 API 访问 `DecimationHorizontal/Vertical`，SP25 当时却使用整数节点 API。GenICam 节点的取值是数字，并不代表节点类型就是 Integer。

修复方式：

- 用 `MV_CC_SetEnumValue` 写入抽取倍率；
- 用枚举读取接口回读 `nCurValue`；
- 严格比较请求值和实际值；
- 任一轴设置、读取或回读不符仍阻止启动，不做静默降级；
- Width/Height 继续使用整数 API。

配置仍保持 2×2，预期 720×540，没有为了通过而擅自改成 1×1。

### 4.3 相机实际结果

修复后真实相机串号 `DA6589759`：

- 输出 720×540、CV_8UC3 BGR；
- 自由运行、曝光 3000 μs、gain 回读约 10.0161；
- 启动后采集和交付 99.9–100.0 FPS；
- 约 10 秒收到 914 张；
- `consumer_skipped=0`、`pool_dropped=0`、`capture_timeouts=0`、`reconnects=0`；
- 退出码 0。

开头的 `XOpenDisplay Fail` 没有阻止无窗口取图。它来自无桌面环境中的某个组件提示，本轮没有把它当作取图失败，也没有为此安装桌面。

Pi 没有图形桌面，直接依赖 OpenCV 本地窗口会出现 X11 显示问题，也无法让电脑看到 Pi 的窗口。因此在独立验收入口增加可选 HTTP 预览：

- 最多约 10 次/秒编码 JPEG，只保留最新图；
- 网络线程有读写期限，慢浏览器不阻塞相机和检测；
- 无框帧仍更新画面，不残留旧框。

电脑访问 `http://192.168.1.105:8080/` 即可看画面。它没有重写检测器，也没有接 Tracker/Aimer；开启预览会增加 JPEG/绘制开销，因此预览运行不作为性能基准。

## 7. 图像方向

首次网页画面中，用户确认相机与装甲板实际都正常摆放，但数字和背景整体倒置。问题不能靠让用户倒拿装甲板解决，也不能只用网页 CSS 翻转，否则模型继续处理倒置图像。

因此在 `HikRobotOptions` 增加默认关闭的 `rotate_180`，当前 `configs/camera.yaml` 设置为 true。驱动在 SDK 转换为 BGR、归还 SDK 缓冲后，对尚未发布的独占槽位原地执行 180 度旋转，再交给所有消费者。sequence、时间戳和 BGR 通道语义不变。

后续截图确认数字和背景已经正立。该修改也意味着正式 Solver 使用的内参与外参必须对应最终旋转后的图像，不能简单照搬未核对的旧标定。

## 8. 真实装甲板为什么会“框多而乱”

方向修正后，真实蓝色 3 号板同一帧出现 3 个框，目标分数约 0.98/0.94/0.91，四角点也没有贴住灯条。仅提高 NMS 或只保留最高分会隐藏一部分重复结果，但最高分框本身的角点仍不准，PnP 仍会产生偏差。

对照原 SP25 后确认：原演示配置的 YOLOv5 路径启用了 `use_traditional: true`，网络候选经过 OpenCV 灯条二次修正；当前 Hailo 入口当时只做 resize、Hailo 推理、解码和 NMS，缺少这一层。因此“原 NX 上框得好”和“Pi 上 Hailo 原始框乱”并不矛盾：模型和检测后处理路径都发生了变化。

为区分模型原始输出和修正器效果，增加 `pi_hailo_hailo_only.yaml`，明确关闭灯条修正。同一现场画面证明：多候选和粗糙四角点在 Hailo 原始结果中已经存在，不是网页绘图制造的。

## 9. 灯条修正器做了什么

新增 `tasks/auto_aim/lightbar_refiner.hpp/.cpp`，由 `tasks/auto_aim/yolo.cpp` 在现有 Decoder/NMS 之后调用。它不是另一个神经网络，也没有恢复 OpenVINO；它使用当前同帧 BGR 原图完成以下工作：

1. 提取亮灯条轮廓；
2. 检查灯条长度、长宽比、方向和是否触碰图像边界；
3. 根据灯条周围红/蓝光晕确定颜色，纯白反光不强行判成目标灯；
4. 检查两灯条的长度比、平行程度、板宽高比和矩形误差；
5. 把网络候选四角与真实灯条端点关联，歧义过大时不强选；
6. 用物理灯条端点重建 Armor，同时更新角点、中心、包围框、宽高比、大小板类型和 Lightbar 字段；
7. 多个网络候选若匹配同一对灯条，只保留目标分数最高者；不同灯条对仍可作为不同装甲保留。

初版修正失败时删除网络候选，移动过程中会人为增加掉框。源码对照原 SP25 后改为：当整帧没有任何可靠修正结果时，回退原 Hailo 候选；一旦存在可靠修正结果，不再把旁边未修正的重复框混回来。这样恢复原 SP25“修正尽力而为”的行为，但也留下边界场景可能回退乱框的当前限制。

## 10. 为什么灰度阈值会截短灯条，以及怎样修复

初版按灰度阈值 150 提取亮区域。两张真实红色装甲原图中，右侧灯条顶端的红通道已经达到 255，但灰度只有约 119–149。原因是 OpenCV 灰度会按通道加权，单独很亮的红色不一定得到同样高的灰度值。结果是灯条顶端被掐掉，修正后的右上角仍落在灯条中段。

修复改为对 BGR 图像的红、蓝通道取较亮值，再做同一阈值分割。阈值数值仍是 150，只改变“亮度来自哪里”；颜色、几何、唯一匹配和候选距离检查都保留。

同一原图验证：

- 样本 1 右上点由约 y=223.895 改善到 y=188；
- 样本 2 右上点由约 y=206 改善到 y=171；
- 两张图均由原来的 2/3 个候选合并为 1 个框；
- Pi 静态复跑分别仍为 1 框，约 95.6/103.2 FPS 的单次输出不作为正式性能基准。

这比调整相机曝光更稳妥：曝光和增益会影响整幅图，而通道修复直接针对“彩色灯条通道很亮、灰度却偏低”的已证实原因。固定阈值是否覆盖所有赛场光照仍未全面验证。

## 11. 编号问题

编号来自 HEF 每个候选的 9 个类别分数，当前解码取最大值。显示的 `confidence=0.99` 是目标存在分数，不是“编号为 sentry 的概率 99%”。

早期三号板曾输出 `sentry`，因此检查了当前映射和青大参考实现；两者一致，没有发现把三号固定翻译为哨兵的表错误。动态抽样进一步证明同一模型能正确输出 `three` 和 `sentry`：

- 完整三号样本 20 帧中 19 帧为 `three`，1 帧瞬时为 `sentry`；
- 完整哨兵样本 17 帧全部为 `sentry`。

因此当前结论是单帧模型分类仍可能跳变，不是类别表整体错位。尚未把 9 个原始类别分数、top1/top2 差值输出到诊断日志，也未训练或替换 HEF。后续完整链路可根据原始分数决定是否增加低差值拒绝或在 SP25 Tracker 层做多帧稳定；不能硬编码 `sentry→three`。

## 12. 09-19 动态抽帧验收

原留样功能每 5 秒最多保存 3 组，无法覆盖近、远、移动、换板和掉框。因此只扩展独立验收程序，新增：

```text
--sample-max
--sample-interval-ms
```

默认值仍为 3 组、5000 ms，旧行为不变。现场运行设置约每 2.5 秒保存，共取得 47 个时点；每组包含模型实际输入的无框 PNG、同帧带框 PNG 和文本结果。`sample-min-detections=0` 使零框时点也被保存，避免只看成功帧。

逐帧视觉结论：

- 无可用目标：1–4、29–30，均正确返回零框；
- 只有一根灯条或目标大部分出画：9、12、27，其中 9、27 零框合理；12 回退了一个不可靠原始大框；
- 右灯条被边界裁切：19，回退了两个交叉原始框；
- 完整装甲：5–8、10–11、13–18、20–26、28、31–47，共 37 帧；全部检出、全部单框、预期编号 36/37；
- 远距离完整装甲 23、24 均正确输出 `blue three small`，角点视觉上贴合；
- 红蓝切换和哨兵/三号切换总体正常。

完整数据见 `build/pi-live-validation/dynamic-review-analysis/summary.md` 和四张 overlay 总览。该结果是间隔抽样，不是逐帧召回率。用户同时在浏览器观察到移动和远距离表现明显改善，可以把当前真实检测前端记为阶段性可用，但不能据此宣布 Tracker 或整套自瞄已经锁定目标。

## 13. 当前剩余问题与为什么暂不继续改

1. **边界回退**：第 12、19 帧说明无可靠双灯条时回退网络候选会留下不准的框。可在以后增加可配置严格模式，但严格拒绝也可能在灯条暂时变暗时增加漏检。当前用户决定在此处暂时收口，保留证据，不立即改变默认行为。
2. **编号单帧跳变**：完整三号样本中出现 1 次 sentry。先保留模型原始语义，后续结合原始类别分数和 Tracker 多帧信息处理，不做错误映射补丁。
3. **连续统计限制**：47 组是抽样；没有保存整段逐帧标签或录像，也没有启动原第 11 部分完整统计。
4. **Tracker 尚未接入本次网页入口**：网页显示每帧检测结果，不是选中目标，也不具备跨帧锁定状态。
5. **标定与方向**：最终 720×540、2×2 抽取、软件旋转 180 度必须和内参/畸变/外参共同核准。
6. **C 板与 IMU**：青大 `xrobot.yaml` 使用 `SharedTopic` 和逻辑 UART `DevC-USB`；SP25 `standard` 当前使用 CBoard/SocketCAN。设备映射、帧协议、话题、四元数顺序、坐标轴和时间同步尚未核对，不能直接照抄名称或数值。
7. **整套自瞄**：Solver、Tracker、Aimer、控制输出、真实运动目标和安全的开火逻辑均未验收。
