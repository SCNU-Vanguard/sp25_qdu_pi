# 9.9 第五、六部分：树莓派海康采集适配

目标以 `树莓派+NPU.md` 为准：**Debian 13 / ARM64 / 2 GiB 内存 / HAILO8L**，相机为 MV-CS016-10UC。开发电脑中的 WSL Ubuntu 22.04 仅用于离线检查。改动分别标注 `[9.9-5]`、`[9.9-6]`，保留 SP25 主流程及解算、跟踪、规划结构。

## 第五部分改了什么

| 位置 | 修改 | 原因及效果 |
| --- | --- | --- |
| `io/camera_frame.hpp/.cpp` | 固定容量 `FrameStorage` 池，单个 `latest_` 引用，单调递增 sequence，条件变量读取 | 旧海康队列容量为 1，满时丢新帧；现在覆盖未消费的旧引用，算法慢时直接拿最新已发布帧 |
| `io/camera.hpp/.cpp` | 增加 `read_frame()`、`stats()`，保留旧 `read(Mat&, timestamp&)` | 主流程通过共享帧引用持有槽位，生产者不会覆盖使用中的像素；其他相机和旧调用接口继续保留 |
| `src/standard.cpp`、`standard_mpc.cpp`、`uav.cpp` | 每轮持有帧引用至处理结束；海康超时返回空引用时停止控制/清空 MPC 目标 | 避免重复处理同一 sequence 或将上一帧当新帧；MPC 仍由原规划线程发自瞄控制 |
| `tools/recorder.cpp` | 通过录像 FPS 门限后才复制待保存图像 | 录像异步线程原先只保留 Mat 头；池复用或检测调试绘图会污染录像，必须使录像拥有独立像素 |
| 两个打符调用位置 | 给含原地调试绘图的打符检测传入副本 | 保持池内图像只读；自瞄取帧路径不因此增加整帧复制 |
| `tests/camera_test.cpp` | 新帧接口、限时运行、默认无显示、每秒统计、可模拟慢消费者 | 去掉逐帧 FPS 日志，提供之后上板可复现的采集验收入口 |

池默认 4 个槽位。若实际为 720×540 BGR8，像素共 `4 × 720 × 540 × 3 = 4,665,600` 字节（约 4.45 MiB），另有少量对象开销、SDK 内部缓存及录像副本。池只在首次确认分辨率时分配像素，后续复用；配置上限为 16 个槽位、总像素不超过 256 MiB。所有槽位都被持有时丢弃本次采集帧并立即归还 SDK 缓冲，不阻塞采集线程。

**引用使用约定：** `CameraFrame` 必须覆盖全部图像使用周期；不能只把 `frame->image` 的浅拷贝留给异步任务，也不能在释放帧引用后再访问那个 Mat。异步任务可以保留完整帧引用；需要写图、独立保存或长期缓存时复制图像。旧海康 `read()` 自动深拷贝，发生超时时清空输出并抛异常；需自动恢复的主循环使用新的 `read_frame()`。MindVision 的兼容实现仍保留原阻塞语义，海康统计不代表其他驱动也已改造。

统计为相机对象存活期累计，重连不归零：

| 指标 | 定义 |
| --- | --- |
| `captured` | 成功取到、通过基础元数据/尺寸检查并尝试申请槽位的 SDK 帧数；包括池满和后续转换失败的帧 |
| `delivered` | 通过新帧读取交付给消费者的不同 sequence 数 |
| `consumer_skipped` | 已发布但尚未交付便被新帧替换，或被重连/停止清除的帧数 |
| `pool_dropped` | 申请槽位时所有槽位仍被持有，主动丢弃的帧数 |
| `read_timeouts` | 消费者等候新帧超时次数；停止唤醒不算超时 |
| `capture_timeouts` | SDK `GetImageBuffer` 返回 `MV_E_NODATA` 次数，与消费者超时分开 |
| `reconnects` | 首次成功启动取流后，再次成功启动取流的次数；不等于插拔次数 |

`consumer_skipped` 不按 sequence 差值计算，因此不会重复计算 `pool_dropped`。SDK 内部丢帧、坏元数据和转换失败不在 `consumer_skipped` 内；有错误时这些计数不构成完整的帧数守恒式，须同时看错误日志。相机单测的 `last_host_age` 是最后成功读取帧的“主机收帧到交付”时间，超时期间并非实时旧帧年龄。

## 第六部分改了什么

海康现在只有一个工作线程创建、配置、取图、停止、关闭和销毁 SDK 句柄，移除原 daemon/capture 两线程共享句柄和按 VID/PID 复位 USB 的做法。按相机串号选择；未配置串号时只接受唯一一台 USB 相机，并在首次选中后固定串号，重连时不跳到另一台相同型号设备。

每次重开都重新设置触发模式、连续采集、手动曝光、手动增益、横纵抽取及帧率；保留原连续白平衡。自由运行设定 `AcquisitionFrameRate`；外触发设置 `TriggerSource`、`TriggerActivation`，关闭内部帧率限制。浮点参数回读检查允许 1% 的设备量化误差，抽取枚举的数值须精确一致，Width/Height 必须符合配置；不支持的必要节点会带节点名和 SDK 错误码报错，并按间隔重试，不会忽略失败。

[Pi相机B·09-15 修复] 初次 Pi 自由运行在无条件 `TriggerSelector=FrameStart` 设置处返回 `MV_E_PARAMETER`，未启动取图。现改为仅外触发模式设置 `TriggerSelector=FrameStart`；自由运行仍严格检查 `TriggerMode=Off`。该修复用户已确认上传、编译和测试，随后 Pi 实测越过此设置，转而在水平抽取处报错，仍为 0 帧。

[Pi相机B-抽取·09-15 修复] 第二次错误为 `DecimationHorizontal failed: 0x80000109`。用户回收的 Pi 随库头文件将其定义为节点不存在，原青大驱动使用数值枚举读写抽取；SP25 原来误用了整数 API。本轮将两轴抽取改为 `MV_CC_SetEnumValue` / `MV_CC_GetEnumValue`，仍严格检查返回值与回读，不调整 2×2 配置或尺寸限制。修改及验证状态见 [09-15 相机验收第 7 节](9.15-pi-camera-validation.md)，尚待此次新版源码同步 Pi 实测。

- 使用 SDK 像素转换输出 **CV_8UC3 / BGR**；原始输入已经是紧密 BGR8 时直接复制入槽位。删除原先仅支持几个 Bayer 格式、直接生成 RGB 的硬编码转换表。
- 每次成功 `GetImageBuffer` 均有对应 `FreeImageBuffer`，包括池满、坏尺寸、转换失败和退出路径。先归还 SDK 原始缓冲，再发布池内图像。
- 初始化失败按成功阶段清理；Stop 或 Close 出错也继续尝试后续清理。清理前撤销未交付旧帧；已被消费者持有的帧仍然有效。
- 自由运行连续取图超时达到阈值时重开；外触发缺少脉冲只等待，不误判为需要重开。两种模式检测到设备断开或其他 SDK 错误都会进入重连。
- 删除采集循环内固定 1 ms 休眠。退出唤醒消费者及重连等待，再等待采集线程结束；SDK 取图有上限超时，实际设备 Open/Close 等内部耗时仍需上板验证。
- 仓库 SDK 的 `MV_CC_SetGrabStrategy`、`MV_CC_SetOutputQueueSize` 文档明确只支持 Windows，本实现不调用。Linux 端限制 SDK 图像节点为 2，并由工作线程持续取流；应用层只保留最新帧，但不能据此宣称相机/USB/SDK 内部延迟为零。

当前模板见 `configs/camera.yaml`，是相机单测配置，不是完整机器人配置：

```yaml
camera_name: hikrobot
exposure_ms: 3.0
gain: 10.0
external_trigger: false
acquisition_frame_rate: 100.0
decimation_horizontal: 2
decimation_vertical: 2
expected_width: 720
expected_height: 540
pool_size: 4
grab_timeout_ms: 100
read_timeout_ms: 250
reconnect_delay_ms: 1000
reconnect_after_timeouts: 10
```

**2×2 抽取后 720×540 尚未真机确认。** 若回读不符，按错误中实际尺寸核对相机 ROI/抽取模式后修正模板。仅调查实际尺寸时可将 expected_width/height 同时设为 0；确认后填写实际数值，再进行对应的标定。输出改变时禁止复用此前校准结果；对象重连后尺寸改变也会报错，须重新创建相机对象。

## 在树莓派上如何验收

先保证 OpenCV、yaml-cpp、spdlog/fmt 开发库，以及能在目标 Debian ARM64 加载的海康 MVS SDK 已就绪。仓库有 arm64 主库，但实际 Pi 的 SDK 安装、辅助库、USB 权限和相机节点支持仍需确认。独立程序不要求 HailoRT、JSON、MindVision 或云台连接。

在工程根目录：

```bash
cmake -S tests/camera -B build/camera-tests -DCMAKE_BUILD_TYPE=Release \
  -DSP_BUILD_HIK_DEVICE_TEST=ON
cmake --build build/camera-tests -j2
ctest --test-dir build/camera-tests --output-on-failure

# 真实海康采集；不接入推理和控制。
./build/camera-tests/hik_camera_test --config-path=configs/camera.yaml --seconds=30
# 实际采集若高于消费速度，应看到 consumer_skipped 增长，而不是旧帧排队。
./build/camera-tests/hik_camera_test --config-path=configs/camera.yaml --seconds=30 --slow-ms=15
# 有图形桌面时检查红蓝颜色、方向、曝光及输出尺寸；性能测试时关闭预览。
./build/camera-tests/hik_camera_test --config-path=configs/camera.yaml --seconds=30 --display
```

若需改用 Pi 已安装的 MVS 主库，可传 `-DHIK_SDK_LIBRARY=/实际路径/libMvCameraControl.so`；头文件须与所用库匹配。本入口使用仓库头文件，不能将任意版本主库替换后假定 ABI 兼容。相机测试按原 logger 规则产生小型日志，默认不录像、不保存图片。

随后测试拔出/重新插入 USB、外触发有/无脉冲、持续运行时内存和各项计数。相机设置 100 FPS 不代表测得 100 FPS，也不代表整条自瞄能达到 70–80 FPS。

## 本机检查与本轮边界

离线测试编译真实 `camera_frame.cpp`、`hikrobot.cpp`；海康 API 的测试替身只存在于测试可执行文件中，真实程序只链接真实 SDK。验证脚本在 `build/part56-validation/check_linux.sh`，结果见同目录 `results.md`。默认测试不下载依赖；可选 `--fetch-json` 仅将本机缺失的 JSON 开发包下载、解包到临时目录，以检查三个主程序源码，不安装到系统。构建临时目录无论成功失败均经路径核对后清理。

本轮没有改动第 2–4 部分的 Hailo/Decoder/Armor 实现，也没有开始第七部分 Tracker 的分辨率修正。完整 YOLO 图像入口仍待后续接通；`t - 1ms` 原有 IMU 对齐暂留，当前帧时间戳只是主机收到 SDK 帧后的 steady_clock，不能声称已经对齐曝光或修好了整个 stale-frame 控制问题。录像在启用时仍有复制和编码开销，生产性能配置将在对应后续部分处理。

本机验证可证明软件边界和模拟异常路径，不能证明 ARM64 真实 SDK 运行、相机输出、实际 HEF 合同、识别精度或整链路 70–80 FPS。
