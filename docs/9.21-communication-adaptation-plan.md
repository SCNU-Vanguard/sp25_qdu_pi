# 09-21：C板串口通信与各运行入口适配计划

> 进度更新：协议合同、独立编解码、统一串口后端、普通/MPC兼容外壳和自动热插拔测试已完成。当前进入“真实 Pi 只读通信”；`tx_enabled`仍为 `false`。实现证据与剩余边界见 [QDU SharedTopic 通信实现与只读验收](9.21-qdu-shared-topic-implementation.md)。

当前物理链路已经确认是“Pi USB CDC串口 → C板UART1”，不是SocketCAN。本计划以保留SP25视觉、跟踪、解算和瞄准主体为前提，把青大SharedTopic协议接到一个统一通信层，再让标准、MPC、无人机和哨兵入口共同使用。协议只实现一次，不在每个兵种源码中复制串口解析、CRC和重连代码。

> 当前代码包审计确认SharedTopic尚未实现，普通入口仍走旧SocketCAN，MPC入口仍走旧`SP`串口协议；不能直接进入真实收发/热插拔测试。证据与可复用边界见 [当前代码包通信适配审计](9.21-communication-code-audit.md)。

## 1. 最终结构

```text
/dev/serial/by-id/usb-QDU-Future_MainCtrl_...
                 │
                 ▼
        串口设备与重连管理
  open/read/write/timeout/hot-plug/state
                 │
                 ▼
         SharedTopic字节协议
 frame header/length/topic id/payload/CRC
                 │
                 ▼
          SP25统一C板语义层
 姿态/时间/模式/弹速/云台状态/裁判信息
        ↑                      ↓
   状态快照与插值          安全控制命令
        │                      │
        └────各运行入口共同调用────┘
```

“各兵种适配”只发生在最上面一层：把旧`CBoard`或`Gimbal`调用换成统一接口，并按兵种读取自己需要的字段。底下的设备打开、SharedTopic解析、CRC、重连和新鲜度判断不能复制多份。

## 2. 阶段一：形成完整协议合同

先从Pi原青大源码确认，不猜测：

1. `DevC-USB`如何映射到实际设备，波特率、8N1/流控和读写超时；
2. SharedTopic帧头、长度、topic ID、payload和CRC；
3. 拆包、粘包、错头、坏CRC后的重新同步规则；
4. `gimbal_quat`、`gimbal_gyro`、`gimbal_accl`的数据结构、单位、轴方向、四元数顺序和时间戳；
5. 弹速、工作模式、射击侧、热量/裁判信息对应的topic；
6. 视觉到电控的云台控制topic，yaw/pitch及速度、加速度字段的单位和绝对/增量含义；
7. `camera_sync_command/result`的用途和时间域；
8. C板启动、复位和序列号/计数器重新开始时的行为。

输出是一张“topic名称 → ID → 方向 → payload字节布局 → 单位 → 更新频率 → 是否必须”的协议表。协议表完成前只读源码和设备，不发送任何报文。

## 3. 阶段二：实现独立SharedTopic串口后端

通信实现分成三部分，便于单独测试：

### 3.1 串口链路

- 使用`/dev/serial/by-id/...`，不写死`/dev/ttyACM0`；
- 初次没插设备时不退出，按有上限的间隔重试；
- 读有超时，析构能及时唤醒并退出；
- 读/写异常进入offline并关闭旧文件描述符；
- 重连后清空半包、解析缓存、旧状态和待发送意图；
- 维护`disconnected/connecting/online/stale/reconnecting`状态；
- 记录连接代次、最后收包年龄、读写错误和重连次数；
- 线程共享状态使用互斥或原子量，不能一边close一边read/write。

### 3.2 SharedTopic编解码器

- 输入任意长度字节块，正确处理半帧、多帧和帧头前噪声；
- 帧长和缓存有上限，坏长度不能导致无限等待或大量分配；
- CRC错误只丢坏帧并重新找帧头；
- topic ID和payload长度必须匹配协议表；
- 解析器只产生已经完整校验的消息；
- 编码器根据协议生成完整帧，不直接发送C++结构体内存。

### 3.3 SP25语义适配

- 将青大四元数转换成Eigen需要的`wxyz`顺序；
- 保存主机收包时间，若协议有板端时间则同时保留，不混用时间域；
- 提供带时间戳的姿态队列和有界插值；
- 模式、弹速、射击侧、云台角速度等通过一次加锁的状态快照读取；
- 每项状态都有有效标志和年龄，断线或过期后不返回旧值；
- 将SP25普通Aimer命令和MPC命令转换成同一青大控制topic；
- 发送入口统一检查online、状态新鲜、TX开关和禁火开关。

## 4. 阶段三：先做通信层自动测试

不接真实C板发送，使用内存字节流或伪终端验证：

- 一帧拆成多次读取；
- 多帧一次到达；
- 随机字节后重新找到帧头；
- CRC错误、错误topic、错误长度；
- 拔线留下半帧，重连后不得和新帧拼接；
- 静默断流后进入stale；
- 初始没有设备，之后出现；
- 读写中断线和反复重连；
- 退出时线程及时结束；
- 重连后旧姿态、弹速、模式和命令全部失效；
- 发送编码逐字节符合青大协议样例。

这一步验证的是代码边界和恢复逻辑，不代表真实C板已经联调。

## 5. 阶段四：真实Pi只读通信

新增独立只读验收入口，只打开SharedTopic并接收，不创建相机/Hailo，也不允许发送：

- 打印稳定设备路径和链路状态；
- 低频显示四元数、模长、姿态消息年龄、模式和弹速；
- 转动云台时检查轴方向和数值连续性；
- C板未插启动、运行中拔出、重新插入和C板重启；
- 至少多轮热插拔，无崩溃、死锁、忙等或旧数据继续有效；
- 只读连续运行至少30分钟。

通过这一阶段后，通信接收才可以给Tracker/Solver使用。

## 6. 阶段五：统一各运行入口

当前源码实际上有两套上层调用：

- `standard/uav/sentry*`使用旧`io::CBoard + SocketCAN`；
- `standard_mpc`及MPC调试入口使用旧`io::Gimbal + SP串口帧`。

二者都迁移到统一C板接口。计划覆盖：

| 入口类别 | 文件 | 需要的数据/命令 |
| --- | --- | --- |
| 标准装甲自瞄 | `standard.cpp` | 图像时刻姿态、模式、弹速、yaw/pitch命令 |
| MPC标准入口 | `standard_mpc.cpp` | 姿态、当前云台角/速度、模式、含速度/加速度计划命令 |
| 无人机 | `uav.cpp`、`uav_debug.cpp` | 姿态、模式、弹速、普通命令；大符路径仍因模型缺失不可用 |
| 哨兵 | `sentry.cpp`、`sentry_bp.cpp`、`sentry_debug.cpp`、`sentry_multithread.cpp` | 姿态、弹速、射击侧/模式、普通命令 |
| 调试入口 | `auto_aim_debug_mpc.cpp`等 | 与相应生产入口同一接口，默认TX关闭 |
| 标定/通信测试 | `handeye_test.cpp`、新的只读板卡测试 | 姿态和时间；不复用会主动发送的旧测试 |

旧`CBoard`和旧`Gimbal`在迁移期可以保留源码用于对照，但Pi生产入口不能同时打开三种后端。全部生产入口迁移后，再决定删除还是退出构建，避免留下一条误用旧CAN ID或旧`SP`协议的路径。

各入口必须使用相同失效规则：

- 没有新姿态，不进入Solver；
- 状态过期，不使用旧弹速和旧模式；
- 相机无新帧或目标丢失，清除控制意图；
- 通信offline时不尝试发送正常控制；
- 重连后先等待连续有效新状态，首个允许发送的命令必须`control=false, fire=false`。

## 7. 阶段六：相机＋Hailo＋姿态，只读零控制

通信接入SP25上层后，先运行：

```text
相机 → Hailo → Armor → Tracker → Solver
                       ↑
              SharedTopic实时姿态
```

强制`tx_enabled=false`和`auto_fire=false`。网页分别画出检测框、Tracker选中目标和PnP/预测点，验证姿态时间、目标状态和坐标方向。该阶段不允许云台响应视觉命令。

## 8. 阶段七：禁火发送与控制验收

协议编码和只读链路通过后才打开TX：

1. 先只发`control=false, fire=false`，确认电控正确解析；
2. 再发控制关闭状态下的零量，检查超时和退出；
3. 在固定安全环境发送受限的小幅yaw/pitch，核对单位、方向和绝对/增量语义；
4. 再验证MPC的速度/加速度字段；
5. 拔线、相机断流、姿态过期和目标丢失时不能持续旧控制；
6. 整个通信适配阶段`fire`硬门控为false。

自动开火不属于通信接通的验收条件。需要等标定、Tracker、Solver、Aimer和失效行为全部通过后再单独决定。

## 9. 阶段八：通信稳定性与部署

- 启动时C板未插，插入后自动online；
- 接收和发送期间分别多轮拔插；
- C板单独重启和设备节点编号变化；
- 静默断流、坏CRC和高频积压；
- 相机/Hailo继续运行时C板重连，彼此不连带重启；
- 只读30分钟及完整禁火链路5–10分钟；
- 固化by-id、协议版本/指纹、Pi专用YAML、日志和启动退出方法。

## 10. 计划完成标准

通信适配完成需要同时满足：

1. 协议每个字段有青大源码或电控文档依据；
2. 所有生产入口使用同一SharedTopic通信实现；
3. 初始无设备、断连、静默断流和重连都不会卡死或使用旧数据；
4. 普通Aimer和MPC命令都按同一实际控制topic正确编码；
5. 多轮热插拔后能恢复，首个命令安全；
6. 只读和禁火实车验收通过；
7. 配置不再依赖旧`can0`、旧CAN ID、`/dev/ttyACM0`或未经确认的`SP`协议；
8. 仍保留SP25上层结构，没有为每个兵种复制一套通信框架。
