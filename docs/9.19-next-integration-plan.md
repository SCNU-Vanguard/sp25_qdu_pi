# 09-19：检测前端之后的 SP25 主线计划

本计划从已经阶段性可用的“海康相机→Hailo→Armor”继续，目标是保留 SP25 Tracker、Solver、Aimer 主体，接通青大树莓派、C 板和实际云台。检测前端当前不继续调参；已知的编号单帧跳变和触边回退先保留证据，在上层连续链路中决定最小处理方式。原第 11 部分完整性能统计继续暂缓。

## 总体依赖顺序

```text
硬件/协议核准
  → 通信断连/重连/热插拔验收
  → 标定与坐标核准
  → 只读姿态 + Camera/Hailo/Tracker/Solver
  → Aimer只计算不发送
  → 禁止开火的控制发送
  → 目标运动/遮挡/重连验收
  → 基本长稳与部署
```

不能先运行现有 `standard`：它会立即构造 `io::CBoard`、等待姿态并发送命令，而且 `standard3.yaml` 中 `auto_fire: true`、旧相机标定和 CAN ID 尚未证明适用于当前硬件。

## D1：核准 C 板物理连接与协议

> 2026-09-21 已开始D1并完成SP25本机源码合同初查；当前第一个现场动作是Pi只读枚举串口设备。记录见 [D1 C板设备与通信协议核准](9.21-d1-cboard-protocol.md)。

> 接线照片和Pi枚举现已确认实际链路为USB CDC串口到C板UART1，当前适配方向为青大SharedTopic串口后端，并统一迁移标准/MPC/无人机/哨兵入口。分阶段实现与验收见 [C板串口通信与各运行入口适配计划](9.21-communication-adaptation-plan.md)。

### 要解决的问题

原青大配置使用 `SharedTopic` / `SharedTopicClient`，逻辑 UART 名为 `DevC-USB`，接收 `gimbal_gyro`、`gimbal_accl`、`gimbal_quat`、`camera_sync_result`、`robot_game_ref`。SP25 `standard` 当前使用 `io::CBoard` 和 SocketCAN，读取 quaternion/bullet-speed CAN ID，并向 `send_canid` 发送 8 字节命令。二者不是只改设备名就能互换的接口。

### 工作内容

1. 在 Pi 只读确认 C 板对应的 `/dev/serial/by-id`、USB VID/PID或 CAN 网卡，不先发送控制。
2. 读取青大 `SharedTopic` 的设备名映射、波特率、帧格式、校验、topic ID、数据字节序和时间戳语义。
3. 读取控制输出实际使用的 topic/报文；现有 `xrobot.yaml` 只明确列出 `camera_sync_command`，尚不能证明云台控制命令从哪里发送。
4. 对照 SP25 `io::Command`：`control`、`fire`、yaw、pitch 的单位、绝对/增量含义和坐标正方向。
5. 形成一份明确协议合同，再决定复用 SocketCAN、复用现有串口 `io::Gimbal`，还是新增一个只做协议适配的 `SharedTopic` C 板后端。

### 通过标准

- 能稳定只读姿态、模式、弹速等实际需要的数据；
- 每个字段的单位、轴方向、字节序、频率和时间参考有代码证据；
- 断开或数据过期能被识别；
- 还不向云台发送运动或开火命令。

## D1B：串口/通信断连、重连与热插拔

这不是最终附加测试，而是 Tracker/Solver 接收真实姿态前的前置门槛。断线后继续使用旧四元数、旧弹速或旧模式，会让后续算法在“看似有数据”的情况下产生错误结果。

### 现有代码已经发现的缺口

- `io::Gimbal` 定义了 `reconnect()`，但当前接收线程没有调用它；接收线程直接调用 `serial_.read`，异常没有在该线程内完成重连闭环。
- 初次打开串口失败时构造函数调用 `exit(1)`，不支持程序先启动、随后插入设备。
- 构造函数同步等待第一帧四元数，没有超时；设备未连接或协议不匹配时可能一直阻塞。
- 写失败只打印警告，没有改变链路状态或触发重连。
- 当前状态没有 `last_rx`、online/stale 状态；断线后旧 yaw、pitch、弹速、模式仍可能被读取。
- 重连后虽然清理了四元数队列，但没有证明解析缓冲、旧控制命令和所有状态都按新连接代次清空。
- `io::SocketCAN` 有守护重开线程，但连接标志和文件描述符需要核对线程安全；发送端没有完整的离线门控，CBoard 也没有姿态/弹速的新鲜度判断，`imu_at` 在断流时可能等待队列。

最终采用 SharedTopic、现有串口 Gimbal 或 SocketCAN 后，只修实际使用的通信后端；不同时保留三套未经验证的重连实现。

### 需要实现的链路状态

```text
disconnected → connecting → online → stale/disconnected → reconnecting
```

并提供：

- 稳定设备身份：串口优先使用 `/dev/serial/by-id` 或等价的 VID/PID＋序列号映射，不能依赖热插拔后可能变化的 `/dev/ttyUSB0`；
- 初始设备缺失时循环尝试连接，不退出整个自瞄进程；
- 有上限且可中断的读超时和重连等待，程序退出不能卡在 sleep/read/join；
- 断开时立即标记离线，使姿态、弹速、模式和同步结果失效；
- `imu_at` 使用有界等待或显式失败结果，不能无限等待下一帧；
- 重连成功后清空半包、解析缓存、四元数队列、旧时间戳和旧控制意图；
- 重新收到足够的新姿态后才允许 Tracker/Solver/Aimer 使用该链路；
- 发送只在链路 online 且数据新鲜时允许；重连后的首个输出必须是“控制关闭、不开火”，不能补发断线前积压命令；
- 通信线程共享状态使用原子量或互斥，避免关闭文件描述符时另一个线程仍在读写；
- 相机/Hailo 与通信故障隔离，C 板热插拔不应无故重启相机或重新加载 HEF。

### 协议解析必须覆盖的异常

- 一帧被拆成多次读取；
- 多帧一次性到达；
- 帧头前有随机字节；
- CRC/校验错误；
- 中途拔线留下半帧；
- 缓冲区持续积压；
- C 板重启后序列/时间重新开始；
- 收包停止但设备文件仍存在的“静默断流”；
- 写入过程中拔线；
- 重连后设备节点名称变化。

解析器应丢弃坏帧并重新寻找帧头，不能因为一次错包永久错位，也不能将半帧和重连后的新帧拼接。

### 需要保留的有限统计

这些是通信验收所需，不属于暂缓的原第11部分完整性能系统：

- 有效收包数、CRC错误数、帧头丢弃字节数；
- 读超时、读错误、写错误；
- 重连尝试、成功次数和当前连接代次；
- 最后一包年龄；
- 当前 link state；
- 因数据过期而拒绝的姿态/命令次数。

日志按状态变化和低频汇总输出，不能在断线重试时每毫秒刷屏。

### 验证顺序

1. 用可控替身/伪终端测试拆包、粘包、错头、坏CRC、半包、静默断流、写失败和退出；
2. 程序启动时 C 板未插，随后插入，确认自动上线；
3. 正常收包时拔线，确认有限时间内进入 offline，算法拒绝旧数据；
4. 重新插入同一设备，确认自动恢复且先保持控制关闭；
5. 热插拔后 Linux 设备编号变化，仍按稳定身份找回正确设备；
6. 接收和发送期间分别重复热插拔，至少完成多轮而无崩溃、死锁或忙等；
7. C 板单独重启，验证半包清理和新连接代次；
8. 只读连续运行至少30分钟，再做相机＋Hailo＋通信联合持续运行。

### 通过标准

- 启动时无设备不会退出或永久阻塞，插入后能自动工作；
- 拔线后及时离线，旧姿态、旧弹速、旧模式和旧控制命令全部失效；
- 重插后无需重启进程即可恢复；
- 多轮热插拔无崩溃、死锁、文件描述符泄漏或CPU忙等；
- 错包不会污染后续正确帧；
- 退出过程能及时结束读线程和重连等待；
- 恢复后的首个控制状态明确为关闭，只有新数据稳定后才重新允许上层工作。

## D2：核准相机标定、外参与图像方向

### 要解决的问题

当前图像为 1440×1080 原生画面经过 2×2 抽取得到 720×540，并在软件中旋转 180 度。青大配置提供一组 1440×1080 内参和 `camera_mount_to_body` 四元数/平移；SP25 `standard3.yaml` 是另一台车的内参、畸变和 `R_camera2gimbal/t_camera2gimbal`。二者均不能直接作为当前最终配置。

### 工作内容

1. 确认 DA6589759、当前镜头、焦距和安装位置是否对应青大标定文件。
2. 明确 2×2 抽取对像素坐标和内参的变换；明确软件旋转 180 度后的主点变化。
3. 若对应关系无法证明，用当前最终相机配置重新采集标定板并标定 720×540 输出。
4. 核对相机到云台/IMU 的旋转、平移、四元数顺序和变换方向。
5. 建立新的 Pi 专用整机 YAML，不覆盖 `standard3.yaml`，并先设置 `auto_fire: false`。

### 通过标准

- 当前分辨率和方向下的内参、畸变来源明确；
- 标定重投影误差合理且记录原始结果；
- 固定装甲在若干已知距离/角度下，PnP 距离和方向误差可解释；
- 坐标轴正方向与 IMU/云台一致。

## D3：建立“只读、零控制”的整链路入口

> 2026-09-22 代码层面已完成（`src/standard_readonly.cpp` + `tests/live_preview.hpp` 叠层 + `tests/communication/qdu_board_simulator.cpp`），**但只在模拟姿态下验证过，真实 C 板仍不回字节**。记录见 [QDU C板模拟器 + D3只读全链路验收](9.22-qdu-cboard-simulator-readonly-chain.md)；该文档 §9 列出了上板前必须先做的构建与短时运行确认。

### 要解决的问题

当前 `hailo_camera_test` 只有相机和检测；现有 `standard` 会创建 CBoard 并发送命令。需要一个可以真实运行 Tracker/Solver、但强制不控制云台的验收入口。

### 工作内容

1. 复用生产 Camera、YOLO、Armor、Tracker、Solver，不复制算法。
2. 接收真实姿态并按图像时间戳取对应姿态；姿态缺失或过期时拒绝求解/输出。
3. 增加只读预览：区分本帧检测框、Tracker 选中目标和预测点，不能把三者画成同一种框。
4. 输出必要状态：检测数量、Tracker 状态、目标编号、PnP 距离、世界坐标、姿态年龄；不做原第 11 部分全套统计。
5. 命令输出强制为空，`auto_fire=false`。

### 通过标准

- 相机、Hailo、姿态、Tracker、Solver 可连续运行；
- 没有姿态或没有新图时不使用旧结果；
- 全程没有云台运动和开火输出；
- 异常能释放相机、Hailo 和通信资源。

## D4：验收 SP25 Tracker 和编号连续性

### 测试场景

1. 单个三号板近、远、左右、上下移动；
2. 单个哨兵板同样移动；
3. 短暂遮挡、移出再进入；
4. 三号与哨兵交替出现；
5. 两块真实装甲同时出现；
6. 单帧编号错误或短时掉框。

### 重点核对

- `detecting → tracking → temp_lost → lost` 状态转换；
- `min_detect_count`、`max_temp_lost_count` 是否适合约 100 FPS；
- 一个错误编号是否导致目标立即重建或跳车；
- 两个目标时的选择规则是否符合期望；
- 没有目标时是否清除旧控制意图。

若单帧 `three/sentry` 跳变确实破坏关联，再输出 HEF 的九类原始分数，并选择最小方案：低差值拒绝、目标内多帧投票或名称迟滞。若 HEF 在错误帧对错误类别有明显高分，记录为模型问题，不能靠类别硬映射解决。

### 通过标准

- 完整单板移动中保持同一目标；
- 短暂漏检按配置进入 temp_lost 并合理恢复；
- 持续丢失后释放目标；
- 单帧编号跳变不造成危险目标切换；
- 多目标选择过程有可复现记录。

## D5：验收 Solver/PnP

### 工作内容

1. 用已知尺寸的小装甲和大装甲分别验证角点顺序与物理尺寸选择。
2. 在若干已知距离、水平角和俯仰角下记录 PnP 输出。
3. 检查重投影图是否回到实际四角点；重点观察倾斜、远距离和画面边缘。
4. 核对 `R_camera2gimbal`、`t_camera2gimbal`、`R_gimbal2imubody` 和实时四元数的乘法方向。
5. 对灯条修正回退的边界乱框，确认 Solver 是否会拒绝；如果不能，再增加可配置严格灯条模式或边界几何拒绝。

### 通过标准

- 已知距离与角度误差在可接受范围；
- 红蓝、三号、哨兵等语义不会改变错误的装甲尺寸；
- 非法、退化或触边四边形不产生可用控制目标；
- 姿态变化时世界坐标方向正确。

## D6：Aimer 只计算、不发送

### 工作内容

1. 使用真实 Tracker/Solver 输出和实际弹速；弹速缺失时明确记录是否使用默认值。
2. 保持 `auto_fire=false`，只显示计划 yaw/pitch、预测时间和命令有效标志。
3. 手动移动装甲和云台，核对 yaw/pitch 正负方向。
4. 核对图像时间、处理延迟、通信延迟和云台响应延迟的定义，不把主机帧龄当成全部端到端延迟。
5. 先校准静态偏置，再验证移动预测；不同时调整大量 MPC/弹道参数。

### 通过标准

- 静止目标命令方向正确、数值有限；
- 无目标、过期图像、无姿态、PnP失败时命令无效；
- 移动目标预测趋势正确；
- 全程不发送开火命令。

## D7：接通控制发送，继续禁止开火

### 工作内容

1. 按 D1 已确认协议实现或选择通信后端。
2. 先发送禁用/零命令，确认 C 板解析和超时处理。
3. 再发送受限的小幅 yaw/pitch 命令，核对实际方向、单位和绝对/增量语义。
4. 验证拔线、程序退出、相机断流、姿态过期和目标丢失时，发送安全无效命令或由 C 板超时释放。
5. `fire` 始终为 false；开火联调放在所有方向和失效行为通过之后。

### 通过标准

- 云台响应方向与计划一致；
- 目标丢失和程序异常不会持续发送旧角度；
- 通信频率、延迟、丢包和重连行为可复现；
- 未发生任何自动开火。

## E：整套自瞄现场验收

### 场景

- 静止目标近、中、远距离；
- 横向和纵向运动目标；
- 遮挡、出画、重新进入；
- 三号/哨兵切换和多目标；
- 相机或通信短时断开与恢复；
- 关闭预览和开启预览分别运行。

### 指标

- 检测、跟踪、解算、瞄准状态正确；
- 启动后实时循环达到目标 70–80 FPS 或更高；
- 无旧帧控制、NaN/Inf、资源泄漏或异常退出；
- 目标丢失能停止控制；
- 有目标时的角度误差和稳定性满足实车要求。

先完成禁火验收，再单独决定开火条件、热量/裁判系统数据和实际射击测试。基础持续运行可做 5–10 分钟，记录现有计数和错误；这不等于恢复原第 11 部分完整性能统计。

## F：部署与收尾

1. 固化 Pi 专用生产 YAML、模型指纹和相机串号。
2. 固化设备映射，避免 `/dev/ttyUSB0` 顺序变化。
3. 明确启动顺序、日志目录、退出和重启方式。
4. 记录可复现构建命令、版本、依赖、测试结果和已知限制。
5. 清理 `build/transfer` 临时包，保留验收日志与必要样本。

## 暂不纳入本轮的内容

- 原第 11 部分完整性能统计系统；
- 无明确需求时的 Hailo 异步流水线、多线程或换模型；
- 当前检测前端继续调阈值、NMS或曝光；
- 大符/能量机关：旧模型已移除，只有取得对应 Hailo 模型和明确需求后再单独适配。

## 下一次开始时的第一步

先做 D1，只读确认 C 板设备与青大 SharedTopic 实现。输出应是一份协议/设备合同，不编译整套 `standard`，不发送云台和开火命令。随后立即完成 D1B 的断连、重连和热插拔能力，再进入标定与只读整链路；不能先让 Tracker/Solver 长期使用一个没有数据新鲜度和重连保证的通信对象。
