# 09-21：QDU SharedTopic 通信实现与只读验收

## 1. 这次确认了什么

从青大源码和现场设备得到的通信合同已经足够实现收发，不再使用猜测：

- 实际物理链路是“树莓派 USB → QDU USB CDC ACM → C 板 UART1”；
- Linux 临时节点是 `/dev/ttyACM0`，生产配置使用带设备序列号的 `/dev/serial/by-id/...`；
- 青大 `User/main.cpp` 将 `DevC-USB`配置为 `115200`、8 数据位、无校验、1 停止位、无流控；
- SharedTopic 包以 `0x5A`开头，协议版本为 `1`，固定头 16 字节，包尾另有 1 字节 CRC8；
- 头部布局为 `prefix(1) + payload长度(3) + topic CRC32(4) + 时间戳us(6) + version(1) + 头CRC8(1)`，多字节字段均为小端；
- CRC8 参数与青大 `libxr::CRC8`一致：初值 `0xFF`，反射多项式 `0x8C`，无末尾异或；
- topic 键是“仅对 topic 名称计算 CRC32”，domain `host`不进入线上的 CRC；CRC32 初值 `0xFFFFFFFF`，反射多项式 `0xEDB88320`，无末尾异或；
- C 板姿态可通过 `ahrs_quaternion`或 `gimbal_quat`回传，payload 是 Eigen/LibXR 四元数对象的 16 字节原始 ABI，线上顺序为 `x,y,z,w`四个 IEEE-754 `float`；
- 视觉控制使用 `target_euler`，payload 是 9 个 `float`：`rol,pit,yaw,rol_dot,pit_dot,yaw_dot,rol_ddot,pit_ddot,yaw_ddot`；
- 机械俯仰轴按青大现有 Aimer 的做法，同时填写 `rol`和兼容字段 `pit`；
- 发射许可使用 `fire_notify`，payload 是 1 字节 `bool`；
- 青大哨兵运行配置明确把 `target_euler`与 `fire_notify`交给 `SharedTopicClient`发往 C 板，所以这两个输出不是推测。

已核对的 topic CRC32 固定值：

| topic | CRC32 |
| --- | ---: |
| `target_euler` | `0x6F0986CB` |
| `fire_notify` | `0x0291AD6B` |
| `ahrs_quaternion` | `0xA6351AEA` |
| `gimbal_quat` | `0xBD0471CC` |
| `robot_game_ref` | `0x33DD3798` |

## 2. SP25 改了什么

### 2.1 独立字节协议

新增：

- `io/qdu_shared_topic_protocol.hpp`
- `io/qdu_shared_topic_protocol.cpp`

它们只负责字节协议，不依赖相机、Hailo 或上层自瞄：

- 按青大格式编码完整包；
- 处理任意拆包、粘包和帧头前噪声；
- 分别校验头 CRC8 与整包 CRC8；
- 限制最大 payload，坏长度不会导致无限等待或按攻击长度分配内存；
- 坏 CRC、坏版本和坏长度后逐字节重新寻找下一帧；
- 只把完整且校验通过的 packet 交给上层。

### 2.2 串口、状态与热插拔

新增：

- `io/qdu_shared_topic.hpp`
- `io/qdu_shared_topic.cpp`

这部分负责：

- 用稳定 by-id 路径以 115200 8N1 打开串口；
- 启动时设备不存在不会退出，按配置间隔继续尝试；
- 读超时有界，程序退出时线程可以结束；
- 读写异常后关闭旧串口对象，清空解析半包、姿态队列和待发送命令，再重新打开；
- 记录打开次数、断开次数、字节数、有效包数、姿态数、无效四元数、未知 topic 和 CRC 错误；
- 使用主机收到姿态时的 `steady_clock`时间保存姿态队列，并对图像主机时间做有界插值；
- 超过 `stale_timeout_ms`没有新四元数时判定姿态过期，正常控制命令不再进入发送队列；
- 断线期间产生的命令不会留到重连后补发；
- 重连后的第一组输出固定为零目标、`fire=false`；
- RX 静默但串口仍可写时只排队一次零目标与禁火，避免持续保留最后一个正常意图；
- 非开火命令先发 `fire=false`再发目标；开火命令先发目标再发 `fire=true`。

原有各兵种配置继续把 `tx_enabled`设为 `false`，用于只读和热插拔验收。新增
`configs/pi_standard3_qdu.yaml`只供当前 Pi 整链集成，它把 `tx_enabled`设为 `true`，由
`standard`主程序发送 Aimer 的真实目标角；`auto_fire`固定为 `false`。

正常发送不是持续构造一个固定零值。链路收到有效姿态、检测建立 Tracker 目标且 Aimer
成功求解时，发送实际非零 yaw/pitch。以下情况仍必须清除目标并禁止开火：没有目标、图像
断流、姿态过期、上层显式停止、串口刚重连以及程序正常退出。QDU payload 没有独立的
`control`位，因此“停止控制”在线上表现为九个目标量归零和 `fire_notify=false`。

### 2.3 保留 SP25 上层接口

`io/cboard.*`保留了原 SP25 普通 Aimer 所调用的 `CBoard`外形，但内部已经从 SocketCAN 换成 QDU SharedTopic。`Command`中的 yaw/pitch 会转换成 `target_euler`，shoot 会转换成 `fire_notify`。

`io/gimbal/gimbal.*`保留 MPC 主程序使用的 `Gimbal`外形，但旧的 `'S','P'` packed 串口帧已移除。它和 `CBoard`共用同一个 QDU 后端，并能传递 yaw/pitch 的角度、速度和加速度。

这使现有标准、MPC、无人机、哨兵和调试入口在重新构建后都共用一份串口协议与重连实现，不需要在各兵种源码中复制通信代码。旧 `io/socketcan.hpp`仍留在源码树作历史对照，但已没有生产类引用，也没有运行时打开 `can0`。

以下配置删除了旧 `can_interface`、三个 CAN ID、`/dev/gimbal`和旧串口 PID 参数，并加入同一 `qdu_communication`块：

- `ascento.yaml`
- `calibration.yaml`
- `demo.yaml`
- `example.yaml`
- `mvs.yaml`
- `sentry.yaml`
- `standard3.yaml`
- `standard4.yaml`
- `uav.yaml`

第一阶段固定：

```yaml
tx_enabled: false

```

## 3. 目前仍然缺什么

这次完成的是通信协议和链路适配，还不能据此宣布整套自瞄完成。

青大已提供的上行 topic 中没有 SP25 旧接口所需的以下实时字段：

- 工作模式；
- 左/右/双枪选择；
- 实时弹速；
- UAV 的 `ft_angle`；
- 独立的当前云台 yaw/pitch 角速度与弹丸计数。

青大 `AimerRefereeSummary`虽有 92 字节裁判摘要，但现有 Aimer 回调也只是继续使用配置中的默认弹速，摘要没有可用的实时弹速。因此当前 SP25 明确使用 `default_mode`和 `default_bullet_speed`，没有伪造反馈。

姿态传输的字节顺序已经确定，但现场仍需确认实际发送的是 `ahrs_quaternion`、`gimbal_quat`还是两者都有，并核对其轴方向。青大哨兵配置会把“x 前、y 左、z 上”的 `ahrs_quaternion`转换成公开本体系；SP25 的 `R_gimbal2imubody`也参与姿态坐标变换。只读测试先确认 topic 和数值连续性，之后再决定最终只保留哪个 topic 以及在哪里完成轴变换。

相机触发同步 `camera_sync_command/result`尚未接入 SP25。当前相机仍按已经验证的自由运行 100 FPS 使用，姿态先以主机收包时间对齐；这不等于完成曝光时刻与 IMU 的硬同步。

## 4. 已完成的自动验证

独立测试工程位于 `tests/communication`，不依赖 Hailo 或相机。

1. `qdu_shared_topic_protocol_test`
   - 核对五个 topic 的固定 CRC32；
   - 用固定十六进制样例逐字节核对编码结果；
   - 穷举一帧的所有两段拆分位置；
   - 检查噪声、粘包、坏 payload CRC 和超长头后的恢复。
2. `qdu_hotplug_sim_test`
   - 用 Linux PTY 模拟 C 板；
   - 100 Hz 发送真实格式的 `ahrs_quaternion`；
   - 运行中关闭 PTY、删除设备链接、建立新 PTY 并恢复发送；
   - 要求监视器检测到断开、至少再次打开一次、继续收到姿态；
   - 要求整个测试发送命令数始终为 0。
3. `qdu_normal_tx_sim_test`
   - 同一个 Linux PTY 中以 100 Hz 向生产通信层发送合法四元数；
   - 同时经生产 `CBoard::send()`提交 yaw=0.25 rad、pitch=-0.125 rad 的非零命令；
   - 在模拟 C 板一侧解析实际串口字节，要求收到 `target_euler`且九个 float 顺序正确；
   - 要求全部 `fire_notify`均为 false；
   - 同时覆盖启动/退出清零，但必须至少观察到一条中间的非零正常命令。

WSL 实测结果：3 项全部通过，总耗时 9.48 秒。该结果证明编解码、重连以及同一串口并行
收姿态/发非零目标的主机侧行为正确，不代替树莓派与真实 C 板验收。

## 5. 树莓派第一轮只读验收

编译完成后运行 `qdu_link_monitor`。常规用法只接受 `tx_enabled: false`配置；它的
`--send-command`参数仅供自动 PTY 字节回归使用，真实 C 板的正常发送统一由 `standard`完成。

正常输出应满足：

- `serial_open=1`；
- `imu_fresh=1`；
- `quaternions`持续增加；
- `ahrs_q`或`gimbal_q`至少一个持续增加；
- `invalid_q=0`；
- `crc_header=0`且`crc_payload=0`；
- `q_wxyz`随云台转动连续变化，模长接近 1；
- `tx_commands=0`。

首次 30 秒通过后，再运行 90 秒并在中间拔下 C 板 USB 约 5 秒后插回。最终应有 `opens>=2`、`disconnects>=1`，重新插入后 `quaternions`继续增加，进程不崩溃、不需要手动重启。

## 6. 正常主链发送入口

本轮不使用“循环发送零值”的板卡测试器。真实入口仍是原 SP25 `src/standard.cpp`：

```text
HikRobot → Hailo YOLO/灯条修正 → Solver/Tracker → Aimer → CBoard → QDU SharedTopic
```

本次为该入口增加的内容均标有 `[9.21-QDU-NORMAL-TX]`：

- 姿态超过 250 ms 未更新时，不再把缓存四元数交给 Tracker/Solver；
- 任何 NaN/Inf 角度在串口层被拒绝，并清除目标；
- 每秒输出检测数、Tracker目标数、`control/fire/yaw/pitch`、RX四元数和TX计数；
- `--seconds=N`可让整链运行 N 秒后经正常析构退出，便于重复验收；
- `Ctrl+C`退出时先发送 `fire=false`和清除目标，再关闭串口；
- 新配置复用已验证的 DA6589759、720×540、旋转180度、100 FPS 和 Hailo灯条修正设置；
- 新配置启用 `tx_enabled:true`，但保持 `auto_fire:false`。

`configs/pi_standard3_qdu.yaml`中的内参和外参只是把原 SP25 参数按2×抽取及180度软件旋转
做了几何换算，目的是在目前没有云台/发射机构的接线下运行整条软件链并观察真实非零报文。
它还没有通过当前镜头的相机标定、手眼标定和云台方向验收。因此本轮可以确认 Pi 成功写出
Aimer 结果，不能据此确认角度精度或允许接入执行器。

日志中出现 `control=1`、非零 `yaw_rad/pitch_rad`且 `tx`持续增加，表示正常算法命令已写入
串口。`tx`只证明 Linux 写调用完成；当前协议没有 C 板 ACK，在没有云台执行器的条件下，
仍无法仅靠 Pi 日志证明 C 板应用层已成功解析该命令。

### 6.1 真实 C 板首轮结果（2026-09-21）

清理两个同时占用串口的旧进程后，`qdu_link_monitor`已能独占并打开稳定的 by-id 设备：
`serial_open=1`、`opens=1`、`disconnects=0`。完整15秒内 `bytes=0`、`packets=0`、
`quaternions=0`，接收模式下 `tx_commands=0`。这证明 USB CDC 枚举、路径和 Linux 打开权限
已经通过，但 C 板到 Pi 的应用数据流当前完全静默；因为连原始字节都没有，尚不能用此次结果
验证或否定主机侧 CRC、Topic key、四元数顺序等解析细节。

随后对照 xrobot-org 官方 `SharedTopic` / `SharedTopicClient` 当前源码：接收端直接阻塞等待 UART
字节并调用 `Topic::Server::ParseData()`；发送端订阅本地 Topic，每次本地发布时直接 PackRaw 后
写 UART，没有上位机订阅握手。因此当前不应在 SP25 端虚构握手包或修改解析门限；需先核对
C 板固件是否实例化发送端、是否把 `ahrs_quaternion`或`gimbal_quat`绑定到 DevC-USB，以及
当前无云台接线时板端是否实际产生姿态 Topic。取得板端工程/配置并恢复非零原始字节前，真实
C 板 RX、同时收发和热插拔验收保持未通过。

## 7. 实车相机后端收敛

真机对照确认：USB 系统能枚举 `2bdf:0001 Hikrobot MV-CS016-10UC`，独立海康程序稳定输出
100 FPS；失败的完整 `standard`则同时加载了 `libMvCameraControl.so`、MindVision 的
`libMVSDK.so`和 libusb，并在海康枚举阶段返回资源申请失败 `0x80000006`。

当前机器人只使用海康相机，因此生产 `io`目标和 `Camera`工厂收敛为 HikRobot 单后端，
不再编译或链接 MindVision、普通 USB Camera、MVSDK 和 libusb，也移除两个无关 USB Camera
测试目标。这样不是隐藏缺失依赖，而是根据真实硬件消除同进程的异厂 SDK 冲突。SP25 的
相机抽象、海康驱动、固定帧池、Hailo、Tracker、Solver 和 Aimer 主体保持不变。

移除 `libMVSDK.so`后真机再次确认 `standard`只加载 `libMvCameraControl.so`，但并发启动仍会在
海康枚举阶段返回 `MV_E_RESOURCE(0x80000006)`；同一时刻独立海康测试仍可正常达到100 FPS。
继续对照已通过的 `hailo_camera_test`后，正式入口改为确定性分阶段启动：先完成日志和 Hailo/
SP25算法对象构造，再启动海康并等待第一帧，最后打开QDU。该顺序不靠固定 sleep，进入主循环
后相机、Hailo和QDU仍并行工作。

后续最小对照进一步确定，初始化顺序不是最终根因：根工程的 `camera_test`在不加载 Hailo、
Tracker、Aimer 或 C 板对象时仍于 `MV_CC_EnumDevices`返回 `0x80000006`。两份程序实际加载的
运行库不同：已通过100 FPS取图的独立测试使用原青大参考工程随附的海康 ARM64
`libMvCameraControl.so`，根工程则使用 `io/hikrobot/lib/arm64`中的另一份同名库。通过
`LD_PRELOAD`仅替换运行库后，根工程同一个 `camera_test`立即成功输出720×540 BGR并稳定约
100 FPS，因而确认问题是仓库内 ARM64 海康运行库，不是相机代码、配置、Hailo或QDU。

正式处理是把这份已经真机验证的海康运行库同步到仓库的固定位置，并让 `io/CMakeLists.txt`
按绝对路径链接该文件；不在部署时保留 `LD_PRELOAD`，也不让正式程序依赖参考工程目录。
修改标记为 `[9.21-PI-HIK-SDK]`。完成同步、重新配置和构建后，仍需在不设置
`LD_PRELOAD`的情况下复测 `camera_test`与 `standard`，才算永久修复验收完成。

只同步主库后的第一次永久复测返回 `MV_E_LOAD_LIBRARY(0x8000000c)`。随库错误头把该码定义为
“动态导入DLL失败”；运行库字符串和原目录清单进一步确认，主库在枚举 USB 时动态加载
`libMvUsb3vTL.so`，取图/转 BGR 还使用同套格式转换和媒体组件。工程随后补齐海康 USB
运行组件及 `CommonParameters.ini`，继续使用系统 `/lib/aarch64-linux-gnu/libusb-1.0.so.0`，
没有重新引入 MindVision 或 GigE 后端。未设置 `LD_PRELOAD`的根工程 `camera_test`随即成功：
720×540 BGR、稳定100 FPS，约3秒收到303帧，人工 Ctrl+C 后退出码0，采集超时、池丢弃和
重连均为0。`io/CMakeLists.txt`同时加入 ARM64 组件存在性检查，缺件改为配置期明确失败，
避免到真机枚举阶段才返回 `0x8000000c`。

随后完整 `standard`已在真机启动：Hailo/SP25对象加载成功，相机收到720×540首帧并继续约
100 FPS取图，QDU串口也成功打开。由于 `rx_q=0`，生产安全门控在Detector之前提前跳过，
未执行该轮检测、Tracker、Solver、Aimer或正常非零TX。独占串口的15秒监视进一步得到
`serial_open=1, opens=1, bytes=0, packets=0, quaternions=0, tx_commands=0`。因此完整入口启动
已通过，真实C板应用数据流和完整自瞄仍未通过；详细时间线和下一步见
[09-21阶段总结](9.21-pi-standard-camera-qdu-session-summary.md)。

同时将 TinyMPC 中弃用的 `Eigen::placeholders::last`更新为 `Eigen::last`，并把 RANSAC 数据
写入改成 pair 原位构造，清除本轮 GCC 14 输出的两项非致命提示。
