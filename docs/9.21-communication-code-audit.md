# 09-21：当前代码包通信适配审计

> 本文记录修改前的审计基线。QDU SharedTopic 后端、统一 `CBoard/Gimbal` 外壳和只读热插拔测试现已实现；当前实现状态见 [QDU SharedTopic 通信实现与只读验收](9.21-qdu-shared-topic-implementation.md)。

## 1. 结论

当前代码包**没有完成青大QDU-Future主控板的SharedTopic串口适配**，因此现在不能直接进入真实收发、热插拔和稳定性验收。

此前第1–10部分完成了OpenVINO清理、Hailo、相机、Armor、Tracker/Target/Solver/Aimer等适配，其中Aimer增加了过期图像停控，Camera增加了新帧和超时处理；这些不是C板字节协议和串口重连适配。

当前通信代码仍是原SP25的两条旧路径：

1. 普通`standard/uav/sentry`入口使用`io::CBoard + SocketCAN`；
2. `standard_mpc`及MPC调试入口使用`io::Gimbal + SP串口帧`。

两条路径都没有读取青大SharedTopic的协议定义，也没有绑定现场确认的`QDU-Future_MainCtrl`稳定by-id设备。

## 2. 直接证据

### 2.1 全仓库不存在SharedTopic实现

排除文档、图片和构建产物后，生产源码中没有以下内容：

- `SharedTopic`；
- `DevC-USB`；
- `QDU-Future`；
- `/dev/serial/by-id`；
- `gimbal_quat`、`robot_game_ref`、`camera_sync_command/result`；
- topic名称到ID和payload的映射；
- SharedTopic帧头、长度或CRC解析。

`tests/topic_loop_test.cpp`测试的是ROS2 topic循环，与青大SharedTopic串口协议无关。

### 2.2 普通生产入口仍使用旧CAN

以下入口构造`io::CBoard`：

- `standard.cpp`；
- `uav.cpp`、`uav_debug.cpp`；
- `sentry.cpp`、`sentry_bp.cpp`、`sentry_debug.cpp`、`sentry_multithread.cpp`；
- `auto_buff_debug.cpp`。

`io::CBoard`内部仍创建Linux `PF_CAN/SOCK_RAW/CAN_RAW`，从YAML读取`can_interface`、三个CAN ID。现有车辆配置仍写`can0`、旧CAN ID和`send_canid=0xff`。

现场照片已确认C板实际通过UART1连接USB串口，CAN1/CAN2没有接线，因此这条实现不能用于当前硬件。

### 2.3 MPC入口仍使用旧`SP`串口协议

以下入口构造`io::Gimbal`：

- `standard_mpc.cpp`；
- `auto_aim_debug_mpc.cpp`；
- `auto_buff_debug_mpc.cpp`；
- `fire_test.cpp`、`gimbal_test.cpp`、`planner_test.cpp`。

它从YAML读取`com_port`，现有配置写`/dev/gimbal`；收发使用两个ASCII字节`SP`、packed C++结构和SP25 CRC16。当前源码没有设置波特率和显式读超时，因此沿用串口库默认9600及默认Timeout。

青大配置使用SharedTopic，目前没有证据表明其帧格式与`SP`结构相同。这条实现也不能直接连接当前C板。

### 2.4 稳定性缺口仍然存在

旧`CBoard`：

- 构造函数无限等待两帧四元数；
- `imu_at()`可能无限等待目标时刻后的姿态；
- 没有online/stale、最后收包年龄和数据有效标志；
- 断线后旧弹速、模式和姿态不会统一失效；
- 发送没有链路状态和数据新鲜度门控。

旧`Gimbal`：

- 首次打开失败直接`exit(1)`；
- 构造函数无限等待第一帧姿态；
- 虽定义`reconnect()`，接收线程没有调用；
- 写失败只记录警告，不切换离线状态或触发重连；
- 重连没有清空全部解析半包、状态、时间戳和旧控制意图；
- 没有静默断流检测和最后收包年龄。

因此即使旧`SP`协议碰巧能收到数据，也还不满足学长要求的断连、重连、热插拔和稳定运行。

### 2.5 当前YAML不能用于安全联调

现有`standard3.yaml`等配置仍含：

- `can_interface: can0`；
- 旧`quaternion_canid/bullet_speed_canid/send_canid`；
- `com_port: /dev/gimbal`；
- 多份配置`auto_fire: true`。

它们不是当前Pi+C板的生产配置，不能通过修改一行设备名后直接运行。

`io/dm_imu/dm_imu.cpp`另有硬编码`/dev/ttyACM0`。它是独立IMU实现，不是QDU主控适配；在当前C板占用`ttyACM0`的现场，若误启动该模块可能打开错误设备。后续Pi配置必须使用稳定by-id，并避免该类临时编号冲突。

## 3. 哪些现有内容可以复用

可以复用：

- `io/serial`的Linux串口基础封装；
- `tools/crc.*`中的CRC函数，但只有确认青大使用同一CRC参数后才能复用算法；
- 旧`Gimbal::read_thread()`中“缓存字节、搜索帧头、处理半包/粘包”的思路；
- SP25的`io::Command`、姿态插值需求和各入口业务结构；
- 已完成的Camera新帧、Aimer过期图像停控原则。

不能直接复用为协议事实：

- `SP`帧头；
- 43/29字节packed结构；
- 默认9600波特率；
- 旧CAN ID和8字节CAN布局；
- `/dev/gimbal`或`/dev/ttyACM0`；
- 旧重连函数；
- 现有主动发送测试。

## 4. 哪些旧测试现在不能运行

- `gimbal_test`会主动发送控制，且可带开火测试；
- `gimbal_response_test`会主动发送旧CAN命令；
- `fire_test`会主动发送旧`SP`协议；
- `cboard_test`只适用于旧SocketCAN收包；
- `handeye_test`依赖旧CBoard姿态；
- `topic_loop_test`是ROS2测试，不是SharedTopic串口测试。

这些程序不能用来判断当前C板SharedTopic是否正常，也不能在未知协议情况下“试运行”。需要新增默认只读、TX硬关闭的板卡测试。

## 5. 现在应该怎么继续

当前不能跳到热插拔验收，因为还没有可连接当前设备、可解析SharedTopic的实现。正确顺序是：

1. 从Pi青大源码提取SharedTopic设备映射和完整协议；
2. 实现串口链路、SharedTopic编解码和统一C板状态接口；
3. 用伪终端/内存字节流测试拆包、坏CRC、静默断流和重连；
4. Pi真实C板只读收包；
5. 真实拔插、重连和30分钟只读稳定性；
6. 迁移所有生产入口；
7. 相机＋Hailo＋姿态只读零控制；
8. 最后才做禁火发送和控制方向验收。

详细实现计划见`docs/9.21-communication-adaptation-plan.md`。
