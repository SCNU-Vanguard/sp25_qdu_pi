# 9.9 第九、十部分：拒绝坏位姿、显式传递处理延迟

目标仍是硬件文档记录的 Debian 13 ARM64 树莓派 + HAILO8L。本轮修改沿用 SP25 的 Solver → Tracker → Target → Aimer 结构，代码分别标记 `[9.9-9]`、`[9.9-10]`。

## 第九部分：PnP 失败不能成为 EKF 观测

`Solver::solve(Armor &)` 从 `void` 改为 `[[nodiscard]] bool`。返回 `true` 才能使用本次位姿；返回 `false` 时，传入 Armor 的位姿字段保持原值，调用方必须丢弃本次观测，不能把旧值当作新解算结果。

| 改动 | 原因与效果 |
| --- | --- |
| PnP 前检查恰好四个有限角点、非退化凸四边形和有效装甲语义 | 拒绝缺点、重合点、共线点、自交及 NaN/Inf；继续使用 LT/RT/RB/LB 对应，不自动猜测或重排模型角点 |
| 检查 `solvePnP` 返回值，捕获 OpenCV 异常 | 无解和 OpenCV 输入异常返回失败，不继续读坏输出 |
| 检查 rvec/tvec、相机正深度、各角点深度以及变换后的 xyz/ypr/ypd | 成功返回仍须满足有限数值和几何约束；拒绝相机后方解及世界坐标球坐标雅可比的轴线奇点 |
| yaw 搜索仅接纳有限重投影误差，全部失败则不提交位姿 | 保留原 IPPE、装甲尺寸、坐标变换和 140° 搜索策略；平衡步兵仍跳过 yaw 优化 |
| 标定加载时检查数组长度、有限性和基本内参格式；IMU 四元数检查后归一化 | 固定长度 Eigen 读取前拦住坏配置；坏 IMU 令本次解算失败，下一帧有效姿态可恢复 |
| 两个 Tracker 入口都检查解算结果 | 初始化从排序后的候选中寻找首个有效观测；更新时删除解算失败的匹配观测；坏高优先级目标不触发成功切换 |

这里检查的是数值与基本几何有效性，不能证明标定准确，也不能识别所有“数值正常但语义标错”的模型输出。OpenCV 的相机坐标 Z 向前，IPPE 要求共面物点；沿用原物点模型，增加正深度判断的依据见 [OpenCV PnP 文档](https://docs.opencv.org/4.x/d5/d1f/calib3d_solvePnP.html)。

Tracker 没有有效新观测时，仍按原 SP25 状态机进入 `temp_lost` / `lost`。短时丢失期间可继续输出历史状态的预测，但不会将坏 PnP 送入 EKF 做测量更新，也不会把这帧计为成功观测。全向转向后的有效观测判断和两个直接调用 Solver 的调试入口也已同步修改。

正常解算先在一个 Armor 副本中完成，全部检查通过后才提交位姿；不会复制整帧像素。前哨站重投影诊断复用同一个 PnP 检查函数，失败返回无穷大，避免另留一条未经检查的解算路径。

## 第十部分：Aimer 只接收明确的延迟秒数

接口改为：

```cpp
aim(targets, bullet_speed, pipeline_delay_s);
aim(targets, bullet_speed, pipeline_delay_s, shoot_mode);
```

`pipeline_delay_s` 相对输入 Target 的状态时刻。Aimer 内部不再读取 `steady_clock::now()`、接收时间戳或使用 `to_now` / 固定 5 ms 分支。

每次计算按以下顺序进行：

1. 调用方用同一主机的 `steady_clock` 测量收帧到进入 Aimer 的时间。
2. Aimer 复制当前目标，预测一次“显式处理延迟 + 原配置补偿”。
3. 每轮弹道迭代从这个已补偿的目标重新复制，只增加本轮估计的飞行时间。保留最多 10 轮和 1 ms 收敛条件，避免累加迭代时间或重复补偿处理延迟。

原 `high_speed_delay_time`、`low_speed_delay_time` 保留；高速判断改用角速度绝对值，使正反方向高速旋转使用相同配置。原 SP25 中其他选板、弹道和低弹速回退策略保留。删除原来预建的 10 份 Target 容器，改为循环内需要时复制。

新增可选配置 `max_host_frame_age_ms`，默认 50 ms，已在 `configs/standard3.yaml` 显式标注。Aimer **入口**帧龄超过上限、为负或非有限，以及无目标/无效预测/不可解弹道时，返回停控命令，调试瞄准点无效；左右枪偏置不会重新给停控命令填入角度。下一次有效输入可以恢复。入口检查不保证命令到电控执行时仍低于 50 ms，也不覆盖哨兵 Decider 独立生成的搜索、转向命令。

### 入口与日志

- 实时调用已同步：`standard`、`uav`、`uav_debug` 和四个 `sentry*` 入口。Aimer 主链的 IMU 查询使用主机收帧时刻，去掉未经当前相机验证的固定减 1 ms 偏移。
- `standard` / `uav` 自瞄分支每秒输出一次 `host_frame_age_ms`；`uav_debug` / `sentry_debug` 将同名字段加入原调试数据。该值在 Aimer 返回后记录，包含本轮 Aimer 计算耗时。
- `tests/auto_aim_test.cpp` 回放新增 `--pipeline-delay-ms=0`，默认只按录像时间推进 Tracker、显式模拟零额外处理延迟。需要模拟 12 ms 时传 `--pipeline-delay-ms=12`。时间转换改用 chrono duration，并检查缺失、非有限、负值、倒退和超范围时间，避免原 int 微秒约 35 分钟溢出。
- 无效瞄准点不再绘图；坏 IMU 时调试入口不使用非有限旋转矩阵重投影。

海康路径的主机收帧时间在 SDK 成功返回帧后记录，涵盖后续转换、等待读取和算法处理；尚不含相机曝光、USB 传输前段或控制器执行时间。**`host_frame_age_ms` 不能称为真实曝光到执行的端到端延迟。** 当前计算也没有测量并回补 Aimer 自身未来的计算时间。真实曝光/IMU 对齐须等待相机时间戳语义和真机验证。

原高低速补偿值可能包含原设备的经验延迟，移植后仍须实测重新核对，避免与显式处理延迟重复包含同一段时间。本轮没有把这些配置猜改成新数值。

`standard_mpc` 的 Planner 与打符 Aimer 是另外的接口，本轮未替换其时间策略。第十一部分的完整 FPS、分阶段耗时、p95/max 等统计也未实施。

## 验证方式与边界

新增 `solver_validity_test`、`solver_failure_test`、`aimer_delay_test`，分别覆盖真实 OpenCV 解算与 Tracker、独立进程的 PnP 故障注入，以及真实 Target/EKF/Aimer/弹道的时间补偿。故障替身仅链接到测试进程。

```bash
# Linux 工程根目录；依赖 OpenCV、Eigen3、yaml-cpp、spdlog/fmt、CMake、G++。
bash build/part910-validation/check_linux.sh
# 只运行跟踪/解算/瞄准五项测试：
bash build/part910-validation/check_linux.sh --tracking-only
```

脚本开启 AddressSanitizer、UndefinedBehaviorSanitizer 和泄漏检查，完整模式还回归 Hailo 输出/Decoder/Armor 及相机池/驱动生命周期，并对非 ROS 入口做 C++ 语法检查。缺少 JSON 头时，仅将发行版开发包下载、解包到临时目录，不安装系统软件。临时构建、合成配置、下载和日志都在退出时验证路径后清理。

实际结果见 [验证记录](../build/part910-validation/results.md)。本机检查不能替代 Pi ARM64 编译及设备验收。真实 HEF 合同、完整 YOLO 接入、相机/IMU 标定和树莓派 70–80 FPS 长稳仍待完成，不能仅凭这两部分的离线测试宣称整包已经可部署运行。
