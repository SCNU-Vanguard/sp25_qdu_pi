# 9.9 第七、八部分：Tracker 分辨率适配与 Target 候选边界

本轮按 `9.9.md` 第七、八部分实施，目标仍为 `树莓派+NPU.md` 中的 Debian ARM64 树莓派。业务修改集中在 `tasks/auto_aim/tracker.cpp`、`target.cpp`，分别标记 `[9.9-7]`、`[9.9-8]`；公开接口、SP25 状态机和 EKF 方程保持原结构。

## 第七部分：不再写死图像中心

原 Tracker 的普通入口和全向感知重载都将图像中心写成 `(720, 540)`，即默认图像为 1440×1080。如果实际图像是 720×540，真正中心是 `(360, 270)`，旧排序会偏向右下方的装甲板。

两个入口现在共用一个比较器、各执行一次 `std::list::sort`：

1. 先比较已有 `priority`，数值越小越优先。
2. 同优先级时，比较 `armor.center_norm` 到 `(0.5, 0.5)` 的距离平方。
3. 优先级和距离均相同，利用 list 稳定排序保留原输入顺序。

第四部分的网络 Armor 构造已经根据实际图像宽、高计算 `center_norm`，本轮直接复用。距离平方保持归一化距离的排序关系，同时省掉平方根；合并排序减少一次列表排序和遍历。没有新增另一套优先级映射或跟踪框架。

**效果：** 720×540、1440×1080 以及其他分辨率可以按相同的相对画面位置选目标。这里使用横纵归一化距离，度量的是相对画面位置，不是固定像素距离；不能据此单独承诺 FPS 增加多少。

如果后续重新启用仅接收两根 Lightbar、没有图像尺寸的传统 Armor 构造，调用方仍须在送入 Tracker 前填写正确的 `center_norm`。当前 Hailo Decoder → 网络 Armor 路径已经具备这个数据；本轮没有给传统入口猜测图像尺寸。

## 第八部分：两块装甲板也能安全匹配

SP25 初始化平衡步兵时使用两面模型，而旧 `Target::update()` 固定读取距离排序后的前三个候选，实际访问了两元素 vector 的第三项。本轮在未修改生产代码前已用 AddressSanitizer 复现 `heap-buffer-overflow`，调用位置在 `Target::update()`。

| 修改 | 原因及效果 |
| --- | --- |
| 将遍历上限改为 `min(3, xyza_i_list.size())` | 两面只读两项；三面读三项；四面仍只匹配距离最近的三面，保留原策略 |
| 局部候选 ID 初始化为 `-1`，最小误差初始化为无穷大 | 明确“尚未匹配”，不使用未初始化变量，也不将异常情况随意指派给第 0 面 |
| 没有有效候选时直接返回 | 不改变 last_id、jumped、切换/更新计数及 EKF，不把无效下标传给更新函数 |
| 匹配前检查 EKF 状态维数和有限性，以及观测 xyz/ypr/ypd 的有限性 | 默认未初始化状态、NaN/Inf 观测不进入匹配；Inf 角度也不会进入旧 `limit_rad` 的循环 |
| 匹配误差须有限，保留原两项角度误差之和 | 非有限误差不能成为候选；正常观测的匹配公式、切换语义和 EKF 更新方程不变 |
| 按声明顺序排列原构造初始化列表 | 消除该构造已有的初始化顺序警告，原值不变 |

这里只增加 Target 更新入口的防护；并未实现第九部分 `Solver::solve()` 的 PnP 成败检查，也没有修改 Solver 返回类型或 Tracker 的观测成功判定。不能把跳过坏更新理解成整条定位链路已经完成无效观测处理。

## 检查内容与运行方式

新增两个独立测试，编译真实 Armor、Tracker、Solver、Target、EKF 和数学工具，不使用假的排序或匹配算法：

- `tracker_resolution_selection`：两个 Tracker 入口 × 四种图像尺寸，检查中心选择、优先级覆盖距离、同分稳定顺序、空/单目标，以及首选装甲板实际用于创建 Target。
- `target_candidate_bounds`：1/2/3/4 项候选的边界、四面仍限制最近三面、平衡步兵两面交替更新 100 次、空候选、27 组 NaN/Inf 观测以及默认未初始化 Target。

测试使用的合成相机参数只生成在构建目录，目的在于让真实 Solver 参与回归，**不能用作机器人的标定配置**。结果和修复前复现证据见 `build/part78-validation/results.md`。

在 Linux 工程根目录执行本轮独立测试：

```bash
cmake -S tests/tracking -B build/tracking-tests -DCMAKE_BUILD_TYPE=Debug
cmake --build build/tracking-tests -j2
ctest --test-dir build/tracking-tests --output-on-failure
```

依赖 OpenCV（core/calib3d）、Eigen3、yaml-cpp 和 spdlog/fmt 开发库；不要求 JSON、HailoRT、海康 SDK 或实际设备。

本轮实际使用以下脚本在原生 Linux 临时目录开启地址、未定义行为和泄漏检查，并回归前六部分的五项离线测试：

```bash
bash build/part78-validation/check_linux.sh
# 仅运行本轮两个跟踪测试：
bash build/part78-validation/check_linux.sh --tracking-only
```

脚本结束时先核对临时目录的规范绝对路径，再清理所有编译产物、合成配置和测试日志。工程内仅保留必要源码、测试、说明及小型验证记录。

完整 YOLO 图像入口、真实 HEF 合同、Pi 原生 SDK/相机验收和整链路 70–80 FPS 仍需后续工作及真机测试。本轮没有改动相机、Hailo、Decoder、Armor 的实现或机器人配置。
