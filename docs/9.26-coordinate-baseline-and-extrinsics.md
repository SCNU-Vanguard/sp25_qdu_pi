## 为什么换矩阵

`io/hikrobot/hikrobot.cpp` 在 BGR 发布前执行 `cv::flip(image, image, -1)`，即左右与上下同时翻转，等价于旋转 180°。
`docs/9.16-pi-camera-orientation.md` 记录的是图像整体倒置，不能由此证明硬件倒置的具体成因。
单独左右镜像只反转一条图像轴，和旋转 180°不同。

此前配置把其他车辆的旧旋转矩阵前两列翻转。若旧矩阵确实是同一设备在旋转前光学坐标系下的实测外参，这样换基有数学依据；但本项目不满足已确认的前提。
image_12 的近似四角点输入现有 Solver 后，旧配置的原始 roll 接近 177°，yaw 优化选到 -70°边界，平均对应角点偏差约 101 px。
只换到理想方向矩阵后，相同近似输入的平均偏差约 5.5 px。该数值是截图近似取点的离线诊断，不能当成真实标定精度。
用户随后用临时配置取得 image_13，并反馈基础跟踪检查良好；这是本次固化调试配置的依据。

## 坐标与参数各自的含义

像素坐标 `(u,v)` 描述目标在图片第几列、第几行，没有直接给出米制距离。
PnP 使用装甲板尺寸、四角点及内参，求出相机坐标中的三维位置和朝向。
最终图像对应的 OpenCV 相机系 C：X 右、Y 下、Z 前；SP25 云台系 G：X 前、Y 左、Z 上。
当前理想旋转使 `(x_G,y_G,z_G)=(z_C,-x_C,-y_C)`，之后还要加平移。

实际代码对应：

```text
相机中的位置 → R_camera2gimbal × 位置 + t_camera2gimbal → 云台中的位置
云台中的位置 → 由真实姿态算出的 R_gimbal2world × 位置 → 解算参考系中的位置
```

世界/解算系在这里主要用于消除云台转动对观测的影响；当前 Solver 没有加入底盘全球平移定位，不能把其输出解释成完整场地地图坐标。
蓝色框是跟踪模型经过逆向转换重新投影到图片的结果，方向错误会影响建模，不能只移动绘制位置来修饰。

| 参数 | 含义 | 当前状态 |
| --- | --- | --- |
| camera_matrix、distort_coeffs | 镜头成像规律与畸变 | 本机内参已录入，基于最终输出图像，不要再额外缩放/旋转一次 |
| R_camera2gimbal | 最终相机系到 SP25 云台系的完整方向转换 | 临时理想方向，实测安装偏角待求 |
| t_camera2gimbal | 相机原点在云台系中的位置，单位 m | 沿用旧值，待实测 |
| R_gimbal2imubody | SP25 云台轴与输入姿态所用轴之间的关系 | 单位阵待验证，不等于所有 topic 的轴都相同 |
| C 板实时四元数 | 描述其定义的本体系相对参考系如何旋转 | 真实数据定义与运行状态待核对 |

模拟器一直发单位姿态时，不同的轴约定可能仍都表现为单位矩阵，所以不能证明真实姿态转换正确。
线上四元数 xyzw / 程序构造 wxyz 是存储顺序问题，不等于坐标轴与旋转方向已经正确。

## 青大公开实现可以如何参考

2026-09-26 查阅的 [QDU ArmorTracker README](https://github.com/QDU-Robomaster/ArmorTracker/blob/master/README.md) 把公开本体系 B 定义为右手系 X 右、Y 前、Z 上。
其相机安装系 M 与相机光学系 C 同原点，M 使用 B 的轴约定；配置 `camera_mount_to_body` 只表示安装偏差，固定 C→M 轴变换在代码内。
[ArmorTrackerModel.hpp](https://github.com/QDU-Robomaster/ArmorTracker/blob/master/ArmorTrackerModel.hpp) 的 `CameraToMountRotation`、`CameraToBodyRotationFromMountExtrinsic` 和 `BodyToWorldRotationFromImu` 实现了这一区分。

SP25 的 `R_camera2gimbal` 已包含固定轴约定转换和安装偏角；二者配置含义不同，不能直接粘贴青大矩阵/四元数或其机器的平移数值。
可以沿用青大对当前固件实际发布数据的定义，在接入 SP25 时统一坐标，而不整体重写 Tracker。
公开仓库的定义不证明用户板上正在运行的固件版本也相同，需与学长确认 topic 的发布者、所描述的物体/轴向、旋转方向与零位。

## 外参下一步的顺序

1. 固定最终相机、镜头、云台及相关姿态传感器的安装。改变安装后旧外参一般需要重测。
2. 恢复真实姿态接收；确认 gimbal_quat / ahrs_quaternion 各自的含义。不能把模拟姿态用于实测手眼求解。
3. 在只读模式下分别检查实际转动与姿态变化，明确 SP25 与固件的轴向、参考零位、旋转方向。单位四元数下观察正常不能代替这一步。
4. 复用 `calibration/capture.cpp` 的照片+姿态采集能力。手眼采图应让标定板相对参考系固定，使相机随云台改变多个姿态，停稳后采集；和内参采图时移动标定板的方式不同。
5. 复用 `calibration/calibrate_handeye.cpp` 或适用的原有求解入口，并检查其固定旋转中心/运动模型假设是否符合实际机械结构。
6. 用独立姿态检查重投影、实测距离和坐标一致性；再把实测 R/t 写回电脑主配置、提交 Git、完整同步 Pi。

现有手眼入口还不能直接照搬命令开跑：

- `calibration.yaml` 当前只包含板尺寸、采图与通信参数，没有手眼解算需要的最新 K/D；应从主配置取内参并结合标定板参数，避免维护多份过期标定值。
- 手眼求解仍直接 `findCirclesGrid`、`imshow`/`waitKey`，尚未复用已改善的圆点检测与无桌面显示路径。
- 7×7 对称圆点板有跨图案方向歧义。现有横向连线只整理绘图副本，不保证各照片采用同一物理圆点作为起点；手眼采集/求解需确认对应一致，不能只看连线方向。
- 本轮只改主配置并分析，尚未修改上述手眼入口。
