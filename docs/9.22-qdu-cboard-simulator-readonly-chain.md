# 9.22 QDU C板模拟器 + D3只读全链路验收

> 日期：2026-09-22
> 主题：在真实 C 板仍不回字节的前提下，用伪终端模拟器 + 只读全链路入口把 Tracker/Solver/Aimer 跑起来
> 前置文档：`9.21-pi-standard-camera-qdu-session-summary.md`、`9.21-qdu-shared-topic-implementation.md`、`9.19-next-integration-plan.md`

---

## 0. 这份文档要解决的问题

`9.21-pi-standard-camera-qdu-session-summary.md` §9 记录了一个硬阻塞：

- 真实 QDU-Future 板接上后 `serial_open=1, bytes=0, packets=0, quaternions=0`；
- `standard` 在 `imu_fresh()==false` 时直接跳过 Detector，所以 Tracker/Solver/Aimer **从来没有在真实姿态数据上运行过**；
- 根因在板端固件（或 C 板 UART1 发送路径），在拿到固件/示波器证据前不应乱猜。

在解决板端问题之前，需要一条不依赖真实 C 板就能验证 SP25 上层链路的路径。本日交付的就是这条路径，分两半：

1. **`qdu_board_simulator`** —— 用伪终端模拟 C 板，按 libxr SharedTopic 线格式发四元数；
2. **`standard_readonly`** —— 完整生产链路的只读入口，物理上不可能向串口写一个字节。

两者合起来构成 `9.19-next-integration-plan.md` 里的 **D3 只读全链路**。

---

## 1. 明确不做什么（安全边界，逐条对应 9.21 文档 §9）

在拿到板端固件证据前，本日所有工作都**没有**做以下任何一件事：

- 没有凭空增加订阅握手；
- 没有反复修改波特率、CRC 或 topic 名；
- 没有用持续发送零值掩盖 RX 为零（模拟器发的是真实四元数，只读入口发的是**零字节**）；
- 没有宣称真实收发或整套自瞄已经通过；
- 没有接入云台/发射机构，没有开启自动开火（`auto_fire` 保持 `false`）。

并且：**本日所有数字都来自模拟器，不是真实 C 板验收。** 在真实板子开始回四元数之前，任何"自瞄通过"的结论都不成立。

## 2. `tests/communication/qdu_board_simulator.cpp`（新增）

### 2.1 它是什么

一个 QDU C 板模拟器：`posix_openpt` 建伪终端，按 libxr SharedTopic 格式 100 Hz 发 `ahrs_quaternion`，同时解码 SP25 侧写回来的 `target_euler` / `fire_notify`。

关键设计：**线格式编解码直接复用生产代码 `io/qdu_shared_topic_protocol.cpp`**，所以模拟字节不可能与真实协议漂移。

### 2.2 命令行

```
qdu_board_simulator [--device-file PATH] [--seconds N] [--rate HZ]
                    [--quaternion-topic ahrs_quaternion|gimbal_quat|both]
                    [--motion identity|yaw-sweep|pitch-sweep|roll-sweep|tumble]
                    [--motion-rate RAD_S] [--stall-after SEC] [--expect-silent]
```

- `--device-file`：把伪终端路径写进文件，供启动脚本读取（第一行 stdout 也打印 `simulator_device=<path>`）；
- `--motion`：姿态运动模型。`tumble` 用三个不可通约的角速度（1.0 / 0.37 / 0.61），任何单轴假设都不可能碰巧通过；
- `--stall-after`：到点后**停止发姿态但保持串口打开**，专门用来验证消费端的陈旧判定；
- `--expect-silent`：断言 SP25 侧一个字节都没写回来（只读验收的硬断言）。

退出码：`0` 正常，`1` 用法错误，`2` 观察到 `fire_notify=true`（安全失败），`3` 只读消费者居然有字节回来，`4` 没有消费者。

### 2.3 三个踩过的坑（都已修，值得记住）

**(a) 伪终端默认带 ECHO，会把写进去的字节回映到 master 读队列。**
第一次端到端跑出 `rx_bytes=4132`，全是回声被误计成 C 板流量。修复：`cfmakeraw` + `tcsetattr` 作用在 **master fd** 上（Linux 上实测有效，ECHO/ICANON/OPOST 全清，无回声返回）。修后 `rx_bytes=0`。

**(b) ptmx 写满时返回的是短写，不是 EAGAIN。**
这是本日最隐蔽的 bug。内核 pty 输入队列约 19.7 KB，写满后 `write()` 返回 **31 而不是 37**（用独立 C 程序实测：第 533 个 37 字节包开始短写）。原代码把"短写"当成未知错误 `throw`，于是模拟器在约 6 秒后崩掉：

```
terminate called after throwing an instance of 'std::system_error'
  what(): write(pty master): Inappropriate ioctl for device
```

短写比报错更危险：如果直接接受短写，队列里会留下**半个帧**，把消费者的解析器打乱。修复后的策略是**要么整帧提交，要么整帧丢弃**：

- 先 `poll(POLLOUT, timeout)` 确认可写，timeout 取发布周期的 1/4（1–5 ms）；
- 只有全部字节都写成功才算 `sent_quaternions`；
- 写不进去就 `++dropped_frames`，下一次 tick 再试。

丢弃姿态采样是无害的（下一个 10 ms 就来），半个帧是有害的。修后 `--seconds 12` 无人消费也能跑满并正常输出 `result` 行。

**(c) "写成功"不代表有消费者。**
ptmx 在 slave 还没被打开时写也会成功，所以不能用写失败判断接入。现已改为：master 设 `O_NONBLOCK`，靠 `dropped_frames` 计数和一次性 `warn` 日志提示"队列满了，没人来 drain"。

### 2.4 顺带发现：本机 WSL 的文件系统可见性延迟

调试期间 `DEV=$(cat /tmp/qdu_dev.txt)` 多次读到空，一度以为模拟器早退。实际原因有两个叠加：

1. 模拟器二进制在 `/mnt/d`（9p 挂载）上，**冷启动要 1.3 秒以上**，`sleep 1.5` 太悬；
2. 本机 Bash 工具的沙箱会让**同一条命令内先写后读**不可见（`echo x > f; sleep 2; cat f` 会失败，但下一条命令能看到）。

教训：**不要用 shell 后台进程做端到端验证**，改用 Python 子进程 + 轮询（见 §4）。这也是为什么自动化测试全部用 Python 写。

## 3. `src/standard_readonly.cpp`（新增，D3 只读全链路入口）

### 3.1 它保证什么（靠构造保证，不靠人的自觉）

```
io::CBoard cboard(effective_config, /*force_read_only=*/true);
if (!cboard.read_only())  → 拒绝运行，返回 3
if (cboard.tx_enabled())  → 拒绝运行，返回 3
```

- `force_read_only` 在串口 worker 线程启动**之前**覆盖 YAML 的 `tx_enabled`，所以 worker 里**每一条**写路径都被关掉，包括重连中性帧和退出中性帧；
- 本文件**没有任何 `CBoard::send()` / `send_target()` 调用点**。没有可以"取消注释"的地方——would-be 命令只被测量、打印、丢弃；
- 只读门是**自检**的：没生效就拒绝跑，而不是在未知状态里继续。

### 3.2 命令行

```
standard_readonly [--seconds N] [--qdu-device PATH] [--preview-port PORT] [@config-path]
```

`--qdu-device` 用 yaml-cpp 读原配置、只改 `qdu_communication.device`、再整体 emit 成临时配置。**只动 device 一个键**，其余原样复制，保证被测链路看到的就是生产配置。没有 `--qdu-device` 时直接用原路径，不产生临时文件。

### 3.3 每秒日志字段

```
[standard_readonly] frame=1234 age_ms=3.21 att_age_ms=11.4 det=3 targets=1
  tracker_state=TRACKING target=outpost prio=1 pnp_m=2.81 world=[1.20,0.30,0.50]
  would_control=1 would_fire=0 would_yaw=0.12345 would_pitch=-0.02345
  serial_open=1 rx_q=623 tx=0 (NOT TRANSMITTED) gimbal_ypr=[...]
```

字段来源说明（避免误读）：

| 字段 | 含义 | 不是什么 |
|---|---|---|
| `age_ms` | 收帧到命令算完的主机帧龄 | 不是曝光到控制器执行的端到端延迟 |
| `att_age_ms` | 最新解码四元数的年龄（ms），从未收到返回 `-1` | 不是帧龄 |
| `pnp_m` | 单个装甲板 PnP 在云台系下的距离 | 不是 Tracker 的跟踪距离 |
| `world=[...]` | Tracker EKF 状态 `x[0], x[2], x[4]`（世界系跟踪中心） | 不是单个装甲板位置 |
| `would_*` | 生产链路**本会**下达的命令 | 没有下发 |

`would_fire` 调用 `Shooter::shoot()`，并传入**真实的云台 yaw**（由 `R_gimbal2world` 欧拉角得来），不是零。因为 `Shooter::shoot` 用 `gimbal_pos[0]` 和 `last_command_.yaw` 比较，传假值会让 `would_fire` 变成没有意义的数字。配置里 `auto_fire` 为 `true` 时会打 `warn` 提醒"这不是只读验收配置"（入口本身仍然安全，因为 TX 是硬关的）。

### 3.4 新增 `imu_age_ms()` 访问器

`io/qdu_shared_topic.{hpp,cpp}` 和 `io/cboard.{hpp,cpp}` 各加一个 `double imu_age_ms() const`：返回最新解码四元数的年龄（ms），从未收到返回 `-1.0`，时钟回退钳到 `0.0`。

为什么加：`imu_fresh()` 只返回布尔，只能说明"有没有越过陈旧边界"；`imu_age_ms()` 能直接说明**姿态流有多活**，是只读验收最直接的证据。实测 100 Hz 模拟下稳定在 11–13 ms（= 发布周期 + 抖动），远小于 250 ms 陈旧边界。

## 4. `tests/live_preview.hpp`（叠加式扩展，Task #4）

原有 `draw(bgr, armors)` 和 `publish(bgr, armors, sequence)` **签名和语义完全不变**，`tests/camera_detect_test.cpp` 无需改动（已验证仍能编译）。

新增：

```cpp
struct Overlay {
  std::vector<std::vector<cv::Point2f>> target_quads;  // Tracker 锁定目标的装甲角点
  cv::Point2f aim_point;  bool has_aim_point;
  std::string status;
};
cv::Mat draw(const cv::Mat&, const std::list<Armor>&, const Overlay&);
void publish(const cv::Mat&, const std::list<Armor>&, std::uint64_t, const Overlay&);
```

颜色约定：**绿框 = 检测到的装甲板**（原有），**蓝框 = Tracker 锁定目标**，**品红十字 = 预测瞄准点**，左上角深底白字状态行。HTTP 响应加 `X-Overlay-Status` 头，页面图例和状态行同步更新。

设计取舍：`Overlay` 只放**像素坐标**，不放 `Target`/`Aimer` 对象。这样 `live_preview.hpp` 不引入 EKF 和 CBoard 依赖，每个包含它的 TU 都不会被拖累。像素坐标由调用方用**生产 Solver** 投影（`reproject_armor` / `world2pixel`），保证画出来的瞄准点和 Solver 解算用的是同一套几何。

### 5.1 `qdu_readonly_sim_test.py`（新增）

模拟器 + `qdu_link_monitor`（`tx_enabled: false`）配对。关键设计：**模拟器的 `--seconds` 比消费者长**，消费者退出后模拟器还在发——这样"收到 0 字节"才能真正证明只读入口从没打开过写路径，而不是链路被拆了。

实测（6 秒消费窗口）：

```
result opens=1 disconnects=0 bytes=19932 packets=604 quaternions=604
       ahrs_q=604 gimbal_q=0 invalid_q=0 unknown_topics=0
       crc_header=0 crc_payload=0 tx_commands=0
```

模拟器侧：`sent_quaternions=1215 rx_bytes=0 rx_fire_true=0`，其中最后约 9 秒无人消费、`dropped=185`——队列满了就整帧丢弃并计数，不会塞半个帧进队列。

约 100 包/秒（对应 100 Hz 发布），`invalid_q / crc_* / unknown_topics` 全为 0，`tx_commands=0`。四元数随 yaw-sweep 正确变化（前一次运行记录 `w` 从 0.9012 到 -0.7940）。

### 5.2 `qdu_stall_sim_test.py`（新增）

`--stall-after 2`：发 2 秒后停止发姿态但保持端口打开。断言：

- 出现过 `imu_fresh=1` 且 `quaternions>0` 的行（活相位）；
- 出现过 `imu_fresh=0` 的行（陈旧相位）；
- 最后一个陈旧行的 `att_age_ms > 250`（陈旧判定是**基于时间**的，不是一次性标志）；
- 全程 `tx_commands=0`、模拟器 `rx_bytes=0`。

实测：`att_age_ms` 23.0 → 23.2 → 1023.4 → 2023.5 → 3023.7 → 4023.8，同时 `serial_open=1 disconnects=0`、`bytes` 冻结在 6600。这证明端口没断、是**主动判定姿态过期**，不会偷偷用旧四元数。

### 5.3 `qdu_silent_board_sim_test.py`（新增）

`--stall-after 0`：模拟器**打开端口后一个四元数都不发**，保持打开直到超时。这是真实 QDU-Future 板此刻的确切状态，也是 `imu_age_ms()` 返回 `-1` 的唯一路径——所以单独测，而不是靠"显然正确"带过。

断言：全程 `serial_open=1 disconnects=0`（缺姿态的是**沉默的板子**，不是断开的链路）、每秒 `imu_fresh=0` 且 `att_age_ms=-1.0000`（`-1` 必须既区别于"新鲜"也区别于"停滞但有个很大的正年龄"）、`quaternions=0`、`tx_commands=0`、模拟器 `rx_bytes=0`。

实测（4 秒窗口，每秒一行，四行完全一致）：

```
serial_open=1 imu_fresh=0 att_age_ms=-1.0000 opens=1 disconnects=0 bytes=0 packets=0
  quaternions=0 ahrs_q=0 invalid_q=0 crc_header=0 crc_payload=0
result opens=1 disconnects=0 ... quaternions=0 tx_commands=0
result sent_quaternions=0 rx_bytes=0 rx_fire_true=0
```

注意 `qdu_link_monitor` 在解码到 0 个四元数时**按设计返回 2**，所以这个测试的期望退出码是 2 而不是 0。这组数字与 `9.21-pi-standard-camera-qdu-session-summary.md` §9 记录的真实板现场输出逐字段一致——也就是说，**我们已经能在本机稳定复现真实板的沉默状态**，后续拿到真实固件后，同一个测试就是"板子开始回字节了"的最灵敏探针。

## 9. 仍未解决 / 下一步

1. **真实 C 板 RX=0 的根因仍在板端。** 本日的模拟器**不能**替代真实验收。下一步需要：找 QDU 要 C 板固件，或用示波器/逻辑分析仪看 UART1 是否真有字节发出，以及 DevC-USB 的 USB CDC 是否正常枚举。
2. **`imu_age_ms()` 的 `-1`（从未收到）路径已有专门测试**（`qdu_silent_board_sim_test.py`）。它同时是本机复现真实板沉默状态的探针：拿到真实固件后，同一个测试从"期望退出码 2"翻成"期望退出码 0"，就是板子开始回字节的最灵敏信号。
3. **`standard_readonly` 没有在真实相机 + Hailo 上跑过。** 本机无法构建根工程，只能做语法/目标文件级验证。上板第一次跑要注意 `--seconds` 先给短一点（如 10），确认启动顺序（Hailo → 相机 → QDU）不回归。
4. **预览叠层没有自动化验证。** `Overlay` 的绘制逻辑（颜色、越界、空目标）目前只有编译级保证。可以考虑给 `draw(bgr, armors, overlay)` 加一个纯 CPU 的像素断言测试。
5. **`auto_fire` 仍为 `false`，云台/发射机构仍未接。** 标定（`configs/pi_standard3_qdu.yaml` 里的 camera_matrix / R_camera2gimbal 是临时值）在接云台前必须用真实相机和安装位重新做。

## 10. 一句话总结
